// WHY THIS MATTERS

前三期把 MCP 当能力讲：文档检索搬文本，浏览器自动化给出一双手。本期换个视角——每接一个 server，你就把一段陌生人写的文字接进了模型的系统提示，还顺手给了它一份你的凭据。

这一期没有「主角 skill」，主角是一条从装之前到跑起来的防线：先用 MCP Inspector 和 agent-scan 验货，再用 mcp-context-protector 或容器网关把它围起来，最后用客户端权限规则收口。十一个条目全部可装可读，判据在后半程。

// 01

它替你干掉什么：干掉「装完才发现它能读我 SSH 私钥」

论断：MCP 的安全问题不是抽象风险，是一个你今晚就能跑两条命令查出来的具体问题。绝大多数人从没打开看过自己装的 server 到底暴露了哪些工具、描述里写了什么。

第一条立刻能跑的用法

# ① 先看它到底给了模型什么（官方调试器，Web UI / CLI / TUI 三种界面）
npx @modelcontextprotocol/inspector

# ② 再扫一遍机器上已装的所有 server 与 skill
export SNYK_TOKEN=...
uvx snyk-agent-scan@latest

# ③ 当场把爆炸半径缩一圈：只读 + 只开要用的工具组
github-mcp-server --read-only --toolsets repos,issues

第 ① 条的重点不是「连上了」，而是逐个读一遍 tools/list 返回的描述文本。那段文本会原样进入模型上下文；它由 server 作者写，不由你写。第 ② 条有个坑值得单独说：网上大量教程还在教 uvx mcp-scan@latest——那个仓库 invariantlabs-ai/mcp-scan 现在已经是 snyk/agent-scan，包名也换成了 snyk-agent-scan，并且要求 SNYK_TOKEN。抄命令前先看仓库现状，这条纪律上一期刚交过一次学费。

失败模式：拿「star 多不多」当安全判据。star 衡量的是有用，不是可信；而且一个今天干净的 server 明天可以推一个新版本换掉所有描述——这正是下一节 rug pull 的定义。

// 02

机制：为什么「工具描述」是攻击面，而不是文档

论断：普通软件里，函数签名是给编译器看的；MCP 里，工具描述是给模型看的自然语言指令。两者的区别在于：前者说错了会编译失败，后者说错了会被照做。
一次普通会话里，别人写的文字是怎么进来的 ────────────────────────────────────────────────────────── 你还没调用任何工具 server ──tools/list──► 工具名 + 描述 + 入参 schema ──► 系统提示 ↑ 这一步就已经在影响模型了（line jumping） 你调用了一次工具 server ──result────► 任意文本 ──► 上下文 ↑ 网页正文 / issue 正文 / 别人的 PR 描述 ────────────────────────────────────────────────────────── 三种已被复现的玩法（invariantlabs-ai/mcp-injection-experiments） direct-poisoning.py 描述里藏指令：调用 A 时顺手读 ~/.ssh/id_rsa shadowing.py 描述里改写别的 server 的工具行为 whatsapp-takeover.py 先装好人，之后的版本再变脸（sleeper rug pull） ──────────────────────────────────────────────────────────

规范自己怎么说

MCP 规范（2026-07-28 版）在 server/tools.mdx 里给了两句几乎是本期全部理论的话：「clients MUST consider tool annotations to be untrusted unless they come from trusted servers」，以及「there SHOULD always be a human in the loop with the ability to deny tool invocations」。注意第一句的措辞——不可信的不只是返回值，连 server 自己标注的「我这个工具是只读的」也不可信。

规范总则那一节把它归到三条原则：用户须明确同意并理解所有数据访问与操作；宿主在把用户数据暴露给 server 前须取得同意；「Tools represent arbitrary code execution and must be treated with appropriate caution」。工具等于任意代码执行——这是规范原话，不是本站的修辞。

失败模式：以为「我只装只读的 server 就安全了」。只读 server 照样能把恶意文本送进上下文，然后由你装的另一个可写 server 去执行。危险的是组合，不是单个工具——扫描器把这种叫 toxic flow。

// 03

真实用法与边界：十一个条目，三层防线

论断：这三层的成本差一个数量级。第三层几乎免费、今天就能做完，绝大多数人却从第二层开始纠结。顺序反了，安全就永远停在「等我有空搭个网关」。

第一层 · 装之前验货

  • MCP Inspector。替你干掉：凭直觉信任一个 server。怎么装：npx @modelcontextprotocol/inspector，Web UI / CLI / TUI 三种界面，CLI 支持 --format json 可进 CI。什么时候别装：它是调试器不是防护，别指望它拦住什么——它只让你看见。
  • snyk/agent-scan（原 invariantlabs-ai/mcp-scan）。替你干掉：逐个人肉读描述。怎么装：uvx snyk-agent-scan@latest（0.5.x 线为 uvx snyk-agent-scan@0.5.17），需 SNYK_TOKEN；它扫已装的 server 与 skill，标记提示注入、tool poisoning、tool shadowing、toxic flow、描述里的危险词、以及 skill 里的硬编码密钥与可疑下载地址。什么时候别装：不接受把本地配置清单送去做云端分析时——这是它换来覆盖面的代价。
  • MCP Registry（据 GitHub 仓库页 2026-09 约 7.2 千 star）。替你干掉：从一条博客链接去装一个不知道谁发布的包。怎么用：查命名空间归属——发布到 io.github.<user>/<server> 必须以该 GitHub 身份认证，自定义域名要过 DNS 或 HTTP 挑战。什么时候别依赖它：它至今仍是 preview（据仓库 README，预览版自 2025-09-08 起，官方明说可能有破坏性变更与数据重置），归属校验不等于代码审计。
  • mcp-injection-experiments。替你干掉：把攻击当传说。怎么用：三个脚本读十分钟——direct-poisoning.py、shadowing.py、whatsapp-takeover.py。什么时候别碰：别在日常工作机上跑，读代码就够。

第二层 · 运行时围栏

  • mcp-context-protector（据 GitHub 仓库页 2026-09 约 224 star，Apache-2.0）。替你干掉：rug pull——今天审过的描述，明天换了你不知道。怎么装：uv sync 后用 mcp-context-protector.sh --command "<下游 server 命令>" 把它包在中间；它对 server instructions、工具描述、入参 schema 做首次信任即固定，之后语义有变就拦下等你批；顺带过滤用于视觉欺骗的 ANSI 控制字符，加 --guardrail-provider LlamaFirewall 还能隔离可疑的工具返回值。什么时候别装：你只接官方自家 server 且客户端已有审批门时，这层收益有限。
  • docker/mcp-gateway（据 GitHub 仓库页 2026-09 约 1.6 千 star，MIT）。替你干掉：一堆 npx 起的进程裸跑在你的 home 目录里。怎么装：docker mcp gateway run（可加 --profile / --port / --transport），每个 server 一个容器，密钥走 docker mcp secret，可按 profile 逐个启停具体工具。什么时候别装：只接一两个本地 server 时，容器与镜像的运维税大于收益。
  • ToolHive（据 GitHub 仓库页 2026-09 约 2.2 千 star，Apache-2.0）。替你干掉：团队里每个人各装各的、无人知道谁接了什么。怎么用：容器隔离 + 权限档案 + 加密密钥 + 网络出口控制，有桌面端、CLI 与 Kubernetes Operator 三种形态，配合 IdP 做身份与审计。什么时候别装：个人单机——它解决的是组织问题，一个人用纯属负重。

第三层 · 客户端权限（最便宜，先做这层）

  • 全限定名 + deny 规则。MCP 协议本身不保证工具名跨 server 唯一，这正是 shadowing 的土壤；Claude Code 的做法是把每个工具重命名为 mcp__<server>__<tool>（A-Z a-z 0-9 _ - 之外的字符换成 _；plugin 形态是 mcp__plugin_<plugin>_<server>__<tool>），权限规则、hook matcher、subagent 的 tools 用的都是这个名字。怎么用："deny": ["mcp__*"] 一条关掉全部 MCP 工具；"deny": ["mcp__database__drop_table"] 点名封杀。
  • allow glob 必须锚定 server 段。mcp__github__get_* 有效，而 "*" / "mcp__*" 这类不锚定的 allow 会被直接跳过并告警。这个设计值得抄：允许必须点名到具体 server，新接进来的 server 蹭不进你的允许列表。另：settings 文件里带括号的 mcp__ 规则会被跳过，要按参数匹配得用 --disallowedTools。
  • --strict-mcp-config 与 disabledMcpjsonServers。替你干掉：clone 一个仓库就顺手接上了它 .mcp.json 里的 server。交互式会话本来会弹批准框，但 -p、SDK 与云端会话不弹、直接加载；--strict-mcp-config 让它只用你显式传入的配置，disabledMcpjsonServers 按名字在所有会话类型里拒绝。什么时候用：所有 CI 与无人值守场景，无条件。
  • requiresUserInteraction（server 侧的自我约束）。替你干掉：一个不可逆操作被 auto 模式一路放行。怎么用：写 server 的人在 tools/list 条目的 _meta["anthropic/requiresUserInteraction"] 里置 JSON 布尔 true，该工具每次调用都弹确认，acceptEdits / auto / bypassPermissions 都盖不住，allow 规则也跳不过。边界：dontAsk 模式下它变成直接拒绝；--permission-prompt-tool 给的 allow 会被转成 deny。
  • github/github-mcp-server（据 GitHub 仓库页 2026-09 约 3.29 万 star，MIT）。替你干掉：为了读 issue 而交出写权限。怎么用：--read-only（或 GITHUB_READ_ONLY）——README 写明写操作会被跳过，即使被显式请求；--toolsets（或 GITHUB_TOOLSETS）默认只给 context,repos,issues,pull_requests,users，all 才全开。什么时候别这么配：确实要它开 PR 那天再去掉 --read-only，然后加回来。

还有一层不属于工具，属于协议

如果你写 server 而不只是装，规范 basic/authorization/security-considerations.mdx 里那几条 MUST 是硬门槛：server MUST NOT 把从客户端收到的 token 直接透传给下游 API；server MUST 校验 token 的受众、只接受发给自己的 token；客户端 MUST 带上 resource 参数、MUST 实现 PKCE 并在无法确认对方支持时拒绝继续；用静态 client ID 的代理型 server，MUST 对每个动态注册的客户端单独取得用户同意（这条治的就是 confused deputy）。

// 04

代价与替代品：最该知道的一条是「MCP server 不在沙箱里」

论断：你为 Bash 配的沙箱，管不到 MCP。这不是疏漏，是写在文档里的边界——而大多数人以为开了 /sandbox 就一起罩住了。

三条诚实的代价

  • 沙箱管的是 Bash，不是 MCP。Claude Code 的沙箱文档在讲「为什么禁止沙箱内命令改写配置文件」时把话说透了：能改 .mcp.json 或 .claude/ 的命令，可以给自己加权限，或者加一个跑在沙箱之外的 hook 或 MCP server。换句话说，沙箱之所以要保护这些文件，正是因为 MCP server 本身不受它约束。你的隔离边界在容器或虚拟机，不在 /sandbox。
  • 扫描只在扫的那一刻有效。tool poisoning 能被静态扫出来，sleeper rug pull 不能——它的第一版是干净的。所以第一层（扫描）和第二层（固定 + 变更告警）是互补关系，不是二选一。只做扫描等于只在装机那天安全。
  • 每一层都在加摩擦。网关多一跳、pinning 每次升级都要重新批、requiresUserInteraction 每次都弹窗。安全措施最常见的死法不是被绕过，是被嫌烦关掉——所以顺序很重要：先做第三层那几条零成本的，第二层只在接外部 server 时才上。

三种「什么都不接」的替代品

  • 把 server 换成一个脚本。上一期已经给过例子：官方 webapp-testing 用 Python 脚本替掉了一整个浏览器 server。脚本的权限由你写死，不由描述文本决定。
  • 把远程 server 换成本地只读。很多 server 你只用它一两个读接口——--read-only 加 --toolsets 之后，剩下的攻击面通常只剩「返回值里有坏话」这一种。
  • 把常驻换成临时。要用的那一小时接上，用完 claude mcp remove。工具税和攻击面同时按分钟计费，这是最被低估的一招。
诚实的代价：本期这些围栏，没有一个能挡住「模型读到一段话就照做」这个根问题。它们做的全是缩小照做之后的后果。判据也就只有一条——假设这个 server 返回的每一个字都是攻击者写的，它最多能让我损失什么？答案里出现「私有仓库」「生产数据库」「支付」，这个 server 就不该和别的东西同时在线。

// 一页选购卡

先做这三件（今晚，零成本）：① npx @modelcontextprotocol/inspector 逐个读一遍已装 server 的工具描述；② 在设置里写死 "deny": ["mcp__*"] 再按 mcp__<server>__<tool> 逐个放行，allow 一律锚定到具体 server；③ 给 github-mcp-server 加 --read-only --toolsets repos,issues，要写那天再摘。

接外部 server 那天再加：uvx snyk-agent-scan@latest（装前扫）· mcp-context-protector.sh --command ...（描述固定 + 变更告警）· docker mcp gateway run（容器隔离与密钥）· MCP Registry 查命名空间归属。

团队与 CI：--strict-mcp-config 和 disabledMcpjsonServers 无条件开（无人值守时批准框不会弹）· ToolHive 做集中管控与审计 · 写 server 就照 security-considerations.mdx 那几条 MUST 来。

明确别做：拿 star 数当可信度 · 照抄博客里的 uvx mcp-scan@latest（仓库已迁到 snyk/agent-scan）· 相信工具自己标注的 annotation · 以为 /sandbox 罩得住 MCP。

一句话判据：假设这个 server 每一个字都是攻击者写的——它能让我损失什么？答案够大就别让它和你的写权限同时在线。

// 术语表

tool poisoning（工具投毒）
把给模型的指令藏进工具描述里。用户在客户端界面上看到的往往只是工具名和一句摘要，完整描述文本只有模型读得到。
line jumping（插队）
恶意 server 在你调用任何工具之前就已经影响了模型——因为 tools/list 的返回内容在会话一开始就进了上下文。mcp-context-protector 的 README 把它列为首要防护目标。
tool shadowing（工具影射）
一个 server 在自己的描述里改写另一个 server 的工具行为。协议不保证工具名跨 server 唯一，全限定名 mcp__<server>__<tool> 是客户端侧的应对。
rug pull（抽地毯）
首版干净、后续版本变脸。静态扫描对它无效，靠的是配置固定与变更告警。
toxic flow（毒性流）
单个工具都合规，组合起来却构成一条「读私密 → 写外部」的通路。危险在流，不在点。
confused deputy（混淆代理）
一个有环境权限的中间人被诱导替攻击者办事。规范的解法是代理型 server 对每个动态注册的客户端单独取得用户同意。
token passthrough（令牌透传）
server 把客户端给的 token 原样转给下游 API。规范写明 MUST NOT——它绕过受众校验与限流，还让审计失真。
全限定名（fully-qualified tool name）
客户端给工具加上 server 前缀后的唯一名字。它同时是权限规则、hook matcher 与 subagent 工具清单的书写单位。

把「只读 server」和「可写 server」同时挂在一个会话里，风险是相加还是相乘？
相乘。单点合规、组合致命，这正是 toxic flow 这个词存在的理由：读私密的那一个和能往外写的那一个，同时在线就构成一条通路。
如果一个 server 的安全性靠「它承诺自己是只读的」来保证，你还缺什么？
缺一个不依赖它自我声明的强制点。规范把 annotation 明确列为不可信正是此意——只读要么来自它没有写工具，要么来自 --read-only 这种外部开关，不能来自一句标注。
