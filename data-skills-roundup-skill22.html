// WHY THIS MATTERS

写作类 skill 装错了，你一眼看得出来；数据类装错了，你看到的是一个格式漂亮的数字。这一类的失败模式是静默的——列名选错、口径取错、过滤条件漏了一条，SQL 照样返回一行结果。更麻烦的是，能救这件事的东西不在任何 marketplace 里：你公司管「活跃用户」叫什么，只有你知道。本期点名十条真实可装的条目（官方插件市场里的、GitHub 上的、官方 skill 里的各占一部分），先给表和命令，后半程再给在它们之间取舍的判据。

逐条说人话

  • ① duckdb-skills（官方市场，作者署名 DuckDB Foundation）：官方目录里对它的描述是「读任意数据文件、挂载并查询 DuckDB 数据库、检索 DuckDB/DuckLake 文档、检索历史会话日志、安装与更新 DuckDB 扩展」。这是全场门槛最低的一条——一堆 CSV/Parquet 扔在目录里就能开 SQL，不用连任何服务。什么时候别装：你的数据只在云数仓里，本地一个文件都没有。
  • ② bigquery-data-analytics（官方市场，作者署名 Google LLC）与 looker（同作者）：一个直连 BigQuery 数据集，一个连 Looker 并用 LookML 说话。后者值得单独注意：LookML 就是一份写下来的口径——你要是已经有 Looker，口径层这件事你比别人先解决了一半。
  • ③ clickhouse（官方市场，作者署名 ClickHouse）：浏览组织/服务/库/表结构，跑只读 SQL，还能看备份与账单。同厂另有 clickhouse-best-practices——28 条按影响排序的建表、查询与写入规则，它不连库，只改模型的写法。自托管 ClickHouse 用 ClickHouse/mcp-clickhouse（据 GitHub 仓库页，2026-09 为 877 星，Apache-2.0；默认 CLICKHOUSE_ALLOW_WRITE_ACCESS=false）。
  • ④ MCP Toolbox for Databases（据 GitHub 仓库页，2026-09 为 16.5k 星，Apache-2.0）：本榜星最多，也是唯一一个正面解决口径问题的。它的主张写在 README 里——比起放开通用 SQL，自定义工具给的是受限访问、结构化查询与语义检索，靠预定义逻辑而不是让模型现编查询来保证安全。你在 tools.yaml 里把「月活怎么算」定义成一个带参数的工具，模型只能调它，编不出第二种算法。覆盖 AlloyDB、BigQuery、Cloud SQL、Spanner、Postgres、MySQL、SQL Server、Oracle、MongoDB、Redis、ClickHouse、Snowflake、Trino 等。什么时候别装：你只是临时查一次——写 YAML 的成本比那次查询高。
  • ⑤ Postgres MCP Pro（据 GitHub 仓库页，2026-09 为 3.3k 星，MIT）：它不只是「能跑 SQL」，而是把 DBA 那套搬了过来——索引健康、缓冲区命中、vacuum 状态、复制延迟的体检；用工业级算法找缺失索引；EXPLAIN 加假设索引模拟（不真建索引就估收益）。两档权限写得很清楚：unrestricted 给开发机，restricted 是只读事务加执行时间上限、给生产。生产库上没有第二个选项。
  • ⑥ DBHub（据 GitHub 仓库页，2026-09 为 3.6k 星，MIT）：一个网关连 Postgres、MySQL、SQL Server、MariaDB、Oracle、SQLite 六种。工具面很克制——execute_sql、search_objects，explain_sql 与 health_check 要显式开；还能配自定义参数化 SQL 工具（和④同一个思路的轻量版）。README 明写护栏是「只读模式、行数上限、查询超时」三件套；诚实交代：它的参数文档站本期被出口策略挡住，确切 flag 名本期不抄，装前自己看它的 Command-Line Options 页。
  • ⑦ mcp-server-motherduck（据 GitHub 仓库页，2026-09 为 523 星，MIT）：本地文件、内存库、S3 上的数据、MotherDuck 云端，同一把 SQL 全能查，不给 token 就是纯本地。和①的区别是①是一组 skill（指令层），它是 MCP server（工具层）——两个都装会在「查本地文件」这件事上打架，挑一个。
  • ⑧ mcp-server-chart（据 GitHub 仓库页，2026-09 为 4.4k 星，MIT）：26 种以上图表——桑基、漏斗、小提琴、鱼骨、思维导图、网络图都在内。两条必须知道的边界：默认调用它提供的免费出图服务，即你的数据出网，介意就自部署再用 VIS_REQUEST_SERVER 指过去；地图类图表依赖高德，只在中国境内可用。
  • ⑨ 官方 xlsx skill（document-skills 插件里）：产出层里最该装的一个，因为它把「不坏文件」写成了硬规矩——必须写公式而不是把 Python 算出的结果硬编进去；写完公式必须跑 scripts/recalc.py（调 LibreOffice 真算一遍），报告 errors_found 不为零就不许交付；XLOOKUP / FILTER / UNIQUE 这类明令禁用（LibreOffice 算不了），改用 INDEX/MATCH。最值得抄进你自己规范的一条：所有假设与硬编码数字必须用单元格批注写明出处。
  • ⑩ jupyter-mcp-server（据 GitHub 仓库页，2026-09 为 1.3k 星，BSD-3-Clause）：让模型在真实的 notebook 里建单元格、执行、读输出，而不是在对话里空想代码。代价是要先起 JupyterLab、装协作插件，版本约束也多。什么时候别装：你没有 notebook 工作流，那 duckdb 加一个 Bash 就够了。
另外两条只做提示 · runekaagaard/mcp-alchemy（据仓库页，2026-09 为 420 星，MPL-2.0）覆盖 SQLAlchemy 能连的一切，但文档里没有只读开关——生产库别用。官方 reference servers 里已经没有 postgres / sqlite 了（现存 everything、fetch、filesystem、git、memory、sequentialthinking、time），教程里还在教你装那两个的，都是过期内容。还有一格本期空着：异常检测方向搜到的几个 skill 仓库，要么零星零 fork，要么只是把几条统计方法写成提示词，没有一个够格点名——这一格宁可留白，也不凑数。
// 02

为什么这十条不能混着比：它们是四层，而最底下那层没人卖

论断：接入层决定它够得着什么，执行层决定它能不能真算，产出层决定能不能交出去——而决定数字对不对的口径层，市面上一个现成的都没有。
产出层 ⑧ mcp-server-chart · ⑨ xlsx → 图和表，能发出去的东西 ↑ 执行层 ① duckdb-skills · ⑦ motherduck · ⑩ jupyter → 真的把数算出来 ↑ 接入层 ②③④⑤⑥ → 字节从你的库里来 ↑ 口径层 ——— 没有人卖给你 ——— → 「活跃用户」到底怎么算

最常见的装法是只装中间两层：连上了库、出得了图，然后每次问同一个指标得到不一样的数。原因不在模型笨，在于它面对的是一个有几千列、没人写过定义的库。企业级 text-to-SQL 的基准 Spider 2.0（ICLR 2025 Oral）把这件事量化了：据其仓库 README（论文口径，2024-11），当时最强的 LLM 在 Spider 2.0 上只解出 6.0%，而同样的模型在 Spider 1.0 上是 86.6%、BIRD 上是 57.4%。三个数放一起才是重点——不是模型不会写 SQL，是真实企业库里「问题→SQL」这一步本来就没有唯一解。（该基准 2026 年榜上的分数已经显著高于这个数；其官网本期被出口策略挡住，未能核现值，故只给论文口径的原数与日期。）

所以这一类的选型顺序和别的类别是反的：先决定口径写在哪，再挑工具。三条真实可走的路，都在上面点过名：④ 的 tools.yaml——把指标定义成带参数的工具，模型只能调、不能改算法；⑥ 的自定义参数化 SQL 工具——同一思路的轻量版；已经有 Looker 的直接用官方 looker 插件，LookML 本身就是一份可执行的口径。三条都走不了，就退到最土的一条：在 CLAUDE.md 里写死几条口径与禁用表，再让 ⑨ 的规矩替你留痕——假设必须写成批注。

⑧⑨ 之所以单列一层，是因为它们只管「好不好看 / 坏不坏文件」，完全不管数字对不对。一张桑基图可以把错误的口径画得非常专业。

翻车现场：装了⑤又装了⑥，两个都连同一个 Postgres。表现是同一个问题两次给出不同的执行路径与不同的行数上限，你还以为是数据变了。接入层一个库只留一个入口，这是硬规矩。
// 03

三分钟验货：打开 README 就能答的六个问题

论断：这一类不看星数看开关。下面六问，任何一条答不上来，就别接你的生产库。
  1. 默认是不是只读？ 答得最好的是 ⑤（--access-mode=restricted 给只读事务加执行时间上限）与 mcp-clickhouse（CLICKHOUSE_ALLOW_WRITE_ACCESS 默认 false）；⑦ 的写权限是你自己加 --read-write 加上去的；mcp-alchemy 这一格是空的。
  2. 有没有行数上限与查询超时？ 没有的话，一句 SELECT * 就能把上下文窗口和数据库连接池一起打满。⑥ 明写有这两道护栏。
  3. schema 怎么进 context？ 是启动时把全库表结构灌进来，还是按需查（⑥ 的 search_objects、③ 的浏览表结构）？几千列的库用前一种，等于每轮都在烧钱。
  4. SQL 看不看得见？ 它必须把实际执行的 SQL 亮出来给你审。看不到 SQL 的数据工具，等于让你签一份看不到条款的合同。
  5. 数据出不出这台机器？ ⑧ 默认走公共出图服务；① ⑤ ⑥ ⑦ ⑩ 都在本地跑。这一条决定了你能不能拿它碰生产数据。
  6. 口径能不能钉死？ 只有 ④ ⑥ 和 looker 这一格是实的。其余的都指望模型每次现编，而它每次都可能编得不一样。
这一节的死线：星数在这一类里参考价值最低。⑧ 有 4.4k 星，可它一行 SQL 都不跑；④ 有 16.5k 星，但你不写 tools.yaml 它就退化成一个普通的 SQL 网关。按你缺哪一层挑，不按榜位挑。
// 04

诚实的代价：这一类最不该整套照搬

论断：数据类工具的边际成本不是 token，是「你对一个错数字的信任」——而这笔账要等到季度复盘才结。

三笔账

  • 工具位与 context 税：接入层每接一个 server 就多一批工具描述常驻每一轮。④⑤⑥⑦ 全装的人不少，实际上你只需要其中一个。装完跑一次 /skill-doctor，看谁在白拿钱。
  • 权限：图省事开了写权限，模型某次把 DELETE 当成清洗步骤跑了，这件事没有撤销键。只读是默认值，不是可选项。
  • 静默错误：这一类最贵的失败模式没有报错——列名选错、口径取错、过滤条件少一条，查询照样成功返回。①⑦⑩ 都不会替你发现这件事，⑧ 还会把它画成一张漂亮的图。

不装任何东西，你还能怎么办

  1. 导出 CSV，交给官方 xlsx skill。 不连任何库，也就没有任何权限风险，而它的公式校验闭环照样生效。
  2. 一个 duckdb CLI 加 Bash 就是执行层。 ① 的价值主要在便利和文档检索，不在能力。
  3. 先写口径，再谈工具。 把你最常问的五个指标的定义写进 CLAUDE.md，连表名和禁用表一起写死——这一步比装任何一个 server 都值钱，而且零成本。
那一格永远空着：④ 能保证模型只调你定义的工具，⑤ 能告诉你这条查询走了哪个索引，⑨ 能保证公式不报错——没有一样能判断你定义的那个口径本身对不对。这一步至今只能人做，而且只能由懂业务的那个人做。

// 一页选购卡

先装这三个：① /plugin install duckdb-skills@claude-plugins-official——本地文件立刻能查，零权限风险。② 连你的库那一个，按库挑：Postgres 用 pipx install postgres-mcp 并务必带 --access-mode=restricted；杂库用 npx @bytebase/dbhub@latest；已经在 BigQuery / ClickHouse 上的直接装官方 bigquery-data-analytics / clickhouse。③ /plugin install document-skills@anthropic-agent-skills——让结果落成公式不坏、假设有批注的 .xlsx。

按需再加：googleapis/genai-toolbox（要把指标口径钉成工具，愿意写 tools.yaml）· antvis/mcp-server-chart（要出图，且接受数据出网或自己部署 VIS_REQUEST_SERVER）· clickhouse-best-practices（你在写 ClickHouse 表）· datalayer/jupyter-mcp-server（你本来就住在 notebook 里）· ClickHouse/mcp-clickhouse（自托管 ClickHouse）· 官方 looker（你已经有 LookML）。

明确别做：给生产库开写权限 · 同一个库同时接两个 server · 把整库 schema 一次性灌进 context · 用 mcp-alchemy 这类没有只读开关的连生产库 · 照着老教程装官方 reference 里早已不存在的 postgres / sqlite server · 以为装完这十条，口径问题就解决了。

// 术语表

口径（metric definition）
一个业务指标到底怎么算：取哪张表、算哪个时间窗、排除哪些人。它决定数字对不对，而它只存在于你公司内部。
text-to-SQL
把自然语言问题翻成 SQL。Spider 2.0 这类企业级基准说明：难的不是语法，是在几千列里选对列与口径。
restricted / unrestricted access mode
Postgres MCP Pro 的两档权限。前者是只读事务加执行时间上限，给生产；后者给开发机。
tools.yaml
MCP Toolbox 的配置文件：在里面把口径定义成带参数的工具，模型只能调用，不能自己另写一套 SQL。
LookML
Looker 的建模语言。它的意义在于口径已经被写下来并且可执行——这是多数公司缺的那一层。
假设索引模拟（hypothetical index）
不真建索引，只让优化器假装它存在，看执行计划会不会变好。Postgres MCP Pro 的索引建议靠它。
recalc 校验
官方 xlsx skill 的收口动作：用 LibreOffice 真算一遍公式，errors_found 不为零就不许交付。
