DAY 64 · TEAMWORK

团队里的 Agent 同事

人机共同开发的操作手册：任务怎么交、评审怎么守、上下文怎么存、效果怎么量

2026-11-14 · BigCat

Agent 可以是作者，不能是负责人。每个 agent PR 背后都要有一个具名的人。

前置 → 本站 Day 34 Human-in-the-loop 工程 · Day 33 大规模 Legacy 代码库的 AI 治理

// WHY THIS MATTERS

Agent 和人协作有三种形态：同步结对（一个人在 IDE 里盯着一个 agent）、异步委派（把 issue 派给云端 agent，回来一个 PR）、频道同事（在团队频道里 @ 它，全组都能看、都能改方向）。第三种以 Claude Tag 为代表：在 Slack 里 @Claude，每个线程起一个临时云沙箱，代码任务通常以一个 draft PR 收尾（公测中，据其文档，2026-11 读取）。形态一变，问题就从「怎么用」变成「怎么分工」。这期是一份能照着做的手册，四件事各给一个可以直接抄走的模板，最后是 30 天落地清单。

// POINT 01

任务单：把「帮我看看」换成可验收的委派

Agent 交回来的质量上限，由交出去的那张任务单决定。

// 背景与原理

先定哪些活能交。四条判据要同时满足：范围说得清（能列出动哪些目录）、有 agent 自己能跑的验证（测试、lint、构建）、出错影响小（能靠 revert 收场）、不依赖只在人脑里的知识。

先交这些暂时别交
过期 feature flag 清理
补测试、修 lint
依赖小版本升级
文档与代码不一致
有稳定复现的小 bug		跨团队接口设计
没有测试覆盖的核心路径
schema、权限、计费
要生产数据才能验证的改动

任务单固定五栏：任务、范围、完成标准、不要做、卡住时。完成标准必须是 agent 自己能检查的命令或事实，否则它会自己宣布完成。

// 实战示例

# 频道里的一条委派消息，五栏齐全
@Claude 仓库 acme/shop
任务：删除已全量 30 天的 flag checkout_v2，保留开启分支的行为
范围：只动 checkout/ 及其测试；不改公共接口
完成标准：
  1. grep -r checkout_v2 无结果
  2. make test-checkout 全绿，把输出贴在线程里
  3. 开 draft PR，描述里写 Requested-by: @alice 和删掉的分支清单
不要做：顺手重构；动其他 flag
卡住时：在本线程提问，不要猜
失败模式：线程里人人都能改方向。Claude Tag 的文档写明，频道里任何人在线程里回复都能引导正在运行的会话，不限于发起人。好处是谁都能纠偏，坏处是范围会被旁人一句话悄悄扩大。团队约定一条：只有发起人改范围和完成标准，其他人只补充事实。另一个坑是进度靠原地编辑的清单显示，Slack 不为编辑发通知，安静的线程不等于没在干活。
进阶资源：Claude Tag Docs · How it works · Claude Tag Docs · Get started
// POINT 02

评审与问责：每个 agent PR 有一个具名的人

谁发起谁负责，谁批准谁共担。PR 作者栏写着机器人，on-call 找的仍然是人。

// 背景与原理

规则一：发起人就是 DRI（直接负责人）。合并后出问题找发起人，所以 PR 描述里必须有 Requested-by。

规则二：堵住「一个人走完全程」的口子。Claude Tag 文档讲得很直白：PR 的作者是 Claude，GitHub「不能批准自己的 PR」这条限制落在 Claude 身上，不落在发起人身上；在只要求一个批准的分支上，发起人可以独自批准并合并。文档给的修法有两个：要求两个批准，或者加一个只针对 claude[bot] PR 的必过状态检查。两种都要同时打开「新提交后作废旧批准」。

规则三：按风险分级，别对所有 PR 用同一把尺子。

级别例子谁批准
低测试、文档、flag 清理发起人以外的任意一人
中业务逻辑改动该目录的 CODEOWNER
高schema、权限、计费先评审计划，再评审 diff

// 实战示例

# .github/workflows/agent-pr-second-review.yml（示意，先在测试仓验证）
# 机器人开的 PR：必须写明发起人，且有发起人以外的一位批准
name: agent-pr-second-review
on:
  pull_request: {types: [opened, edited, synchronize]}
  pull_request_review: {types: [submitted, dismissed]}
jobs:
  check:
    if: github.event.pull_request.user.type == 'Bot'
    runs-on: ubuntu-latest
    permissions: {pull-requests: read}
    steps:
      - env:
          GH_TOKEN: ${{ github.token }}
          PR: ${{ github.event.pull_request.number }}
          REPO: ${{ github.repository }}
        run: |
          REQ=$(gh pr view "$PR" -R "$REPO" --json body -q .body \
                | grep -oiE 'Requested-by: *@[A-Za-z0-9-]+' | sed 's/.*@//')
          [ -n "$REQ" ] || { echo "missing Requested-by: @user"; exit 1; }
          N=$(gh pr view "$PR" -R "$REPO" --json latestReviews -q \
              "[.latestReviews[]|select(.state==\"APPROVED\" and .author.login!=\"$REQ\")]|length")
          [ "$N" -ge 1 ] || { echo "need an approval from someone other than @$REQ"; exit 1; }
失败模式：橡皮图章。Agent PR 的数量上来以后，评审会退化成点赞。三个对策：每人同时在飞的 agent PR 不超过 3 个；单个 PR 超过 400 行先拆；每周抽两个已合并的 agent PR 做深审。让 AI 做第一道评审可以滤掉机械问题，但它不算那一位「发起人以外的批准」。
进阶资源：Claude Tag Docs · Configure GitHub（Require a second approval） · GitHub Docs · About protected branches · GitHub Docs · About code owners
// POINT 03

共享上下文：把纠正写进仓库，不要写进聊天

口头纠正只管这一次，写进指令文件才管以后每一次。

// 背景与原理

Agent 每次从零开始，团队的隐性知识它一概不知。载体是仓库根目录的指令文件：AGENTS.md（多家工具通用的约定）或 CLAUDE.md。把它当代码管：agent 犯了一次同类错误，就提一个 PR 改这个文件，和代码一样评审。文件本身该写什么、各家工具怎么加载，见 Skill 8；这里只讲团队怎么让它一直是对的。

四节就够，按重要性排：

  1. 验证：改完必须跑哪些命令，各要多久。这一节最值钱，agent 能自己跑的验证越多，人越不用当测试机。
  2. 禁区：哪些目录和文件不能动。
  3. 约定：PR 多大、行为变更要不要挂 flag。
  4. 踩过的坑：每条带日期和 PR 链接，方便日后清理。

验证慢的大系统要多做一步：把验证分级写清楚（秒级静态检查、分钟级单测、小时级回放），并规定「本地验证不了就停下来说明缺什么」。没有这句话，agent 会交一个没验证过的 PR 并写上「已完成」。

// 实战示例

# AGENTS.md 骨架：只写 agent 需要而代码里读不出来的东西
## 验证（改完必须跑，把结果贴进 PR）
- make lint                 # 秒级
- make test-<module>        # 分钟级，只跑你动过的模块
- 本地验证不了的改动：停下，在线程里说明缺什么

## 禁区（需要改就先问）
- schema/**、billing/**、已发布的 *.proto 字段

## 约定
- 一个 PR 只做一件事，超过 400 行先拆
- 行为变更挂 flag，默认关
- PR 描述必须有 Requested-by: @发起人

## 踩过的坑
- <日期> <一句话>，见 <PR 链接>
失败模式：指令文件长成没人读的 wiki。规则互相矛盾、一次性的偏好也写进去，agent 的遵守率反而下降。每季度清一次，像清过期 flag 一样删掉不再成立的条目；文件太长就按目录拆成子文件。另外注意，Claude Tag 运行中的线程读不到之后才授予的仓库，文档建议授权后开新线程。
进阶资源：AGENTS.md · 开放约定说明 · Claude Code Docs · Memory（CLAUDE.md）
// POINT 04

节奏与度量：先量排队，再谈提速

写代码变快以后，时间都花在等上：等评审、等验证、等发布。

// 背景与原理

三个固定节奏：

  • 每天：发起人当天处理自己发起的 agent PR，不留过夜。
  • 每周 20 分钟回顾：把被打回或回滚的 agent PR 逐个归因到四类之一，每类对应修一处。
  • 随时：同一个模块同时只有一个写者，人或 agent 都算，在线程里认领。
归因修哪里
任务单不清改任务单模板
缺团队知识给 AGENTS.md 加一条
缺验证补测试或检查
本就不该交改「暂时别交」清单

只盯四个数：agent PR 从开到合的时间、首次通过率（不用人改就能合的比例）、合并后的回滚率（和人写的对比）、人均在飞 PR 数。别量代码行数和 agent PR 总数，这两个数只会涨。

// 实战示例

# 过去 30 天的 agent PR：开到合的中位小时数，单提交直接合并的比例（首次通过率的粗略代理）
gh pr list --state merged --limit 200 \
  --search "author:app/claude merged:>=2026-10-15" \
  --json createdAt,mergedAt,commits \
| jq '[.[] | {h: (((.mergedAt|fromdate) - (.createdAt|fromdate)) / 3600),
              c: (.commits|length)}]
      | {n: length,
         median_hours: (map(.h) | sort | .[length/2|floor]),
         one_commit_ratio: ((map(select(.c == 1)) | length) / length)}'
失败模式：产出涨了就宣布成功，没发现评审队列和回滚率也在涨。发布周期以周计的大系统尤其要小心：agent 几分钟交出 PR，然后和所有改动一起排几周的队。这时候再加 agent 只会加长队伍，该投的是更快的验证信号：分级测试、flag 级灰度、自动给出「安全 / 不安全 / 证据不足」的结论。

// 越界 · 跨学科的联想

  • 心理学 · 责任分散与社会惰化：Darley 与 Latané 1968 年的实验发现，在场的人越多，每个人出手相助的概率越低；Latané 等人 1979 年又测到，一起喊叫鼓掌时人均出力随人数下降。频道里人人都能引导 agent，正是这种局面，所以要点名一个发起人。不像在于：agent 不会偷懒，会偷懒的是以为别人已经看过的评审者。
  • 复杂性科学 · 共识主动性（stigmergy）：Grassé 1959 年研究白蚁筑巢时提出，个体不直接沟通，靠在环境里留下痕迹来协调。指令文件和线程就是这样的痕迹。不像的是，白蚁的痕迹会自然挥发，过期的规则得有人去删。
  • 领导力 · 机组资源管理（CRM）：1977 年特内里费空难后，航空业把「副驾驶敢不敢质疑机长」做成了训练科目。任何人都能在线程里叫停 agent，是同一种设计；区别是这里被质疑的一方不会觉得丢面子。
  • 佛学 · 羯磨：僧团的重要决定要在大众面前公开宣告、公开征询，白四羯磨是一次提议加三次征询。任务在频道里公开发起、公开收尾，同样把过程摊在众人眼前；不同的是羯磨要全体无异议，线程只要没人喊停。

// 十条要点

  1. 人和 agent 协作有三种形态：同步结对、异步委派、在团队频道里 @ 它的频道同事。
  2. 能交给 agent 的任务要同时满足四条：范围清楚、可自行验证、出错影响小、不靠隐性知识。
  3. 任务单固定五栏：任务、范围、完成标准、不要做、卡住时；完成标准必须能由 agent 自己检查。
  4. Claude Tag 线程里任何人都能改方向，团队要约定只有发起人能改范围和完成标准。
  5. 发起人就是直接负责人，agent PR 的描述里必须写明 Requested-by，合并后出问题找这个人。
  6. 在只要求一个批准的分支上，发起人能独自批准并合并 Claude 的 PR，需要用分支保护堵住。
  7. 评审按风险分三级：低风险找任意第二人，中风险找 CODEOWNER，高风险先评审计划再评审 diff。
  8. Agent 犯一次同类错误，就提 PR 修改 AGENTS.md，其中「验证」一节最值钱。
  9. 每周回顾把被打回的 agent PR 归因到任务单、团队知识、验证、不该交四类，每类修一处。
  10. 发布慢的大系统里再加 agent 只会加长队伍，该优先投资的是更快的验证信号。

// 30 天落地清单

  1. 第 1 周 · 装护栏：选一个频道和一个仓库；打开分支保护和 Requested-by 检查；写第一版 AGENTS.md，只写「验证」和「禁区」；记下四个度量的基线。
  2. 第 2 周 · 小范围跑：只交「先交这些」里的任务，全部用五栏任务单；发起人当天处理 PR；每人在飞不超过 3 个。
  3. 第 3 周 · 第一次回顾：把被打回和回滚的 PR 逐个归因，每个修一处；上线三级风险评审。
  4. 第 4 周 · 做决定：对比基线。首次通过率高、回滚率不高于人写的，就扩大任务类型；时间主要花在等验证上，就先补验证，不加 agent。

// 术语表

DRI（Directly Responsible Individual）
直接负责人：对一件事的结果负责的那一个具名的人。
draft PR
草稿状态的 pull request，标记为尚未准备好合并。
branch protection（分支保护）
GitHub 对指定分支设置的合并前置条件，如批准数和必过检查。
CODEOWNERS
仓库里声明「哪些路径归谁评审」的文件。
AGENTS.md
放在仓库里、写给编码 agent 看的说明文件，多家工具都读。
首次通过率
agent 交出的 PR 不经人修改就能合并的比例。
stigmergy（共识主动性）
个体通过改变共同环境来间接协调的机制。

// 深入思考

发起人能批准自己发起的 agent PR，是漏洞还是合理设计？
看你把发起人当成什么。如果当成作者，那是自己批自己，等于零评审。如果当成第一位评审者，那么发起人确实读过 diff，是一次真评审。差别在于发起人有确认偏误：任务是自己提的，倾向于认为结果是对的。所以低风险改动可以接受单人，其余要第二双眼睛。
人写代码越来越少，还评审得动吗？
这是 Day 59 讲的技能衰退问题在团队层面的版本。评审能力来自写的经验，长期只审不写会退化。可行的做法是保留一部分核心模块由人亲手写，并让每周深审成为固定动作，而不是有空才做。
验证要几周的系统里，这份手册还剩什么用？
任务单、问责和指令文件照样成立，它们决定 PR 的质量。失效的是「快」：agent 省下的几小时，相对几周的验证周期可以忽略。这种系统的正确顺序是先把验证信号做快、做成 agent 能调用的接口，再谈扩大 agent 的使用面。
要不要给 agent 也设「绩效」？
设给 agent 没有意义，它不会因此改变行为。有意义的是把同样的数字当成团队流程的体检：首次通过率低，说明任务单或指令文件有问题；回滚率高，说明验证有缺口。被考核的是人搭的这套系统。
