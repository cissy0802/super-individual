DAY 62 · SECURITY

专用网安模型与漏洞发现成本的坍塌

能力侧的地面在移动：你依赖的开源库，正被这种量级的模型扫描

2026-10-05 · BigCat

找漏洞变便宜之后，补丁窗口、依赖升级节奏、报告质量这三件事的默认假设都要重算。

前置 → 本站 Day 24 提示注入 · Day 50 LLM 安全护栏与沙箱

// WHY THIS MATTERS

本站安全格子此前讲的都是防自己被打：Day 24 防注入，Day 50 建护栏。这一期讲另一侧——攻防能力本身在变。2026 年 2 月 Anthropic 披露 Claude Opus 4.6 在开源库里找出并验证了 500+ 个未知高危漏洞；3 月与 Mozilla 合作，两周在 Firefox 里找到 22 个漏洞。8 月 10 日 OpenAI 发布专为网安工作流训练的 GPT-5.6-Cyber，只经 Daybreak Red 准入发放；9 月 2 日 Google 跟进 Gemini 3.8 Flash Cyber，同样只发给 Fairwind 计划的审核通过者。三家走到了同一个形态：能力分档，准入即控制面。对超级个体，这不是"要不要申请 Red"的问题，而是你的依赖树、升级节奏和补丁窗口，都建立在"找漏洞很贵"这个已经失效的前提上。

// POINT 01

拒答率不是能力：专用化有代价

GPT-5.6-Cyber 把"愿意做"从 1.5% 拉到 95%，却在自家的"找漏洞 + 写报告"评测上输给了通用版。

// 背景与原理

OpenAI 用内部指标 Advanced Cybersecurity Completion Rate 衡量模型在利用链开发、认证绕过、提权这类请求上的完成率：标准防护下的 GPT-5.6 Sol 为 1.5%，经 Daybreak Blue 放宽后为 2.0%，前代 GPT-5.5-Cyber 为 57.3%，GPT-5.6-Cyber 为 95.0%。注意这个指标量的是意愿，不是准确率。同一份发布里，GPT-5.6-Cyber 在内部 Vulnerability Discovery and Report Writing 评测（找到可利用的严重漏洞、写出能跑的 PoC、提交高质量报告）上反而不如 Sol，官方给的原因是它"有时产出更短、更不详细的漏洞报告"。

工程含义：意愿和能力是两根独立的轴。专用微调在意愿轴上大幅前进，却在"写得完整"这根轴上倒退了。这是微调的老规律：你调的分布之外，总有东西被挤掉。选模型前先判断你的任务卡在拒答还是卡在能力：审自己的仓库、查依赖、读 diff 找注入点，通用模型在授权语境下基本不拒；只有写利用链、做绕过验证这类活才会撞到 1.5% 那面墙。

// 实战示例

# 通用模型做防御审计：把授权范围、输出契约、置信度写死
你在审计我本人拥有的仓库 ./src（授权范围：仅此目录，不联网）。
任务：找出可被外部输入触达的内存安全 / 注入 / 认证缺陷。
对每个发现输出 JSON：
{"file":..., "line":..., "class":"CWE-xxx",
 "reachability":"外部输入如何到达这里，逐跳列出调用链",
 "repro":"最小复现输入或测试用例（必须给出，给不出则 confidence ≤ 0.3）",
 "confidence":0.0-1.0, "fix":"最小补丁"}
宁缺毋滥：没有可复现路径的猜测，放进单独的 "hypotheses" 数组，不进 findings。
失败模式：把完成率当能力榜读，会选错模型；下游如果有人消费报告（工单、披露邮件），专用模型的"更短报告"会直接变成分诊成本。另一个坑是以为拿不到 Red 就落后——防御侧 80% 的活在通用模型 + 好的审计提示词上就能跑，真正的差距在验证流水线，而不在模型档位。

// POINT 02

"找到便宜、利用昂贵"的差距正在关上

3 月 Anthropic 说发现比利用便宜一个数量级、但这个差距不会持续太久；8 月就有模型把两个 V8 漏洞串成了沙箱逃逸。

// 背景与原理

Firefox 合作的数字值得细看：Opus 4.6 两周扫了约 6,000 个 C++ 文件，提交 112 份报告，Mozilla 认定 22 个漏洞、其中 14 个高危，在 Firefox 148 中修复。但团队花了约 4,000 美元 API 额度尝试写 PoC 利用，几百次尝试只成功两次。Anthropic 的结论是"找漏洞的成本比写利用低一个数量级"，并补了一句：照进展速度，这个差距不太可能长久。

五个月后，OpenAI 用 GPT-5.6-Cyber 研究 V8，找到两个可以串联的未知漏洞：优化编译器在把值转成整数时跳过了一个安全检查，undefined 会变成一个意外的大数，再被当作数组下标，编译器以为它在界内而省掉边界检查，于是可以越界读写；第二个漏洞用来逃出 V8 堆沙箱。前者被分配为 CVE-2026-15903（CVSS 8.8，Chrome 150.0.7871.128 修复）。对防守方，这意味着"公开修复 → 有人写出利用"的时间在缩短，你的补丁延迟（patch lag）成了主要风险：浏览器自动更新还好，但捆绑 Chromium 的 Electron 应用、钉死版本的容器镜像、半年没动的 lockfile，都在这个窗口里裸奔。

// 实战示例

# 量出你自己的补丁延迟：哪些已知漏洞有修复版本、公告挂了多少天你还没升
osv-scanner scan source -r . --format json 2>/dev/null \
| jq -r '.results[].packages[] | .package as $p | .vulnerabilities[]
    | [ $p.name, $p.version, .id,
        ([.affected[]?.ranges[]?.events[]?.fixed // empty] | first // "no-fix"),
        (((now - (.published | sub("\\.[0-9]+"; "") | fromdateiso8601)) / 86400) | floor) ]
    | @tsv' \
| sort -t$'\t' -k5,5nr | column -t
# 第 4 列有版本号、第 5 列天数大 = 优先处理；"no-fix" 单独列出看是否需要替换依赖
失败模式：osv-scanner 只看得见已入库的公告。AI 把发现成本打下来之后，最大的增量会落在没人维护的库上：漏洞被找到、甚至被公开，却永远没有修复版本，也可能永远不进数据库。"扫描全绿"只说明已知问题处理完了。另外，published 是公告日期而非修复日期，严格的延迟指标需要再对上修复版本的发布时间。

// POINT 03

依赖升级拆成双车道：版本更新冷却，安全修复插队

"快升"防的是已知漏洞，"慢升"防的是投毒包；两个诉求不冲突，只要别用同一条规则管。

// 背景与原理

漏洞发现变便宜带来两股相反的压力。一边是 CVE 变多、利用变快，要求更快升级；另一边是供应链投毒——恶意版本往往在发布后不久被研究者和自动扫描识破，要求新版本先放一放。很多团队的做法是一刀切地"每周一统一升级"，结果两头都没照顾到。

正确的做法是拆车道，而主流工具已经内置了这个区分。Renovate 的 minimumReleaseAge 让每个新版本等满指定时长才提 PR，文档明确写着安全更新绕过所有 minimumReleaseAge 检查；vulnerabilityAlerts 生成的 PR 还会无视 schedule 和按小时的限流，直接插队。Dependabot 的 cooldown 选项同理：只作用于版本更新，不作用于安全更新。

// 实战示例

// renovate.json：常规更新冷却 7 天、major 冷却 14 天；安全修复自带快车道
{
  "extends": ["config:recommended"],
  "minimumReleaseAge": "7 days",
  "internalChecksFilter": "strict",
  "packageRules": [
    { "matchUpdateTypes": ["major"], "minimumReleaseAge": "14 days" }
  ],
  "vulnerabilityAlerts": { "labels": ["security"], "prConcurrentLimit": 5 },
  "osvVulnerabilityAlerts": true
}
# .github/dependabot.yml：等价写法（cooldown 不影响 security updates）
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule: { interval: "daily" }
    cooldown:
      default-days: 7
      semver-major-days: 14
失败模式：快车道只在有公告时才触发，回到上一点的盲区。Renovate 的 OSV 告警只覆盖直接依赖，传递依赖要靠 GitHub 的 Dependabot alerts 或 osv-scanner 补位。安全修复开 automerge 要谨慎，文档警告错误的告警可能导致修复 PR 反复翻转。还有一个反直觉的点：冷却期越长，你越依赖别人当金丝雀——如果大家都设 14 天，第 14 天才是真正的首发日。
进阶资源：Renovate Docs · Minimum Release Age · GitHub Docs · Dependabot options reference（cooldown）
// POINT 04

瓶颈从"发现"搬到了"验证"

发现便宜了，验证没有便宜：一份没有复现路径的 AI 报告，是把成本转嫁给维护者。

// 背景与原理

同一年里有两个对照鲜明的数据点。curl 在 2026 年 1 月 31 日关闭了 HackerOne 漏洞赏金，Daniel Stenberg 的理由是低质量、疑似 AI 生成的报告太多，2025 年的提交里只有约 5% 是真漏洞。另一边，Anthropic 的 500+ 个漏洞每一个都由团队成员或外部研究者验证过；即便如此，Firefox 那次 112 份报告对应 22 个确认漏洞。前沿实验室的流水线尚且需要大量人工分诊，个人跑一遍模型就提交，噪声只会更大。

对超级个体，这条线有两头。作为报告者：用 AI 扫别人的代码，"能复现"是门票，没有复现的发现只能当线索。作为维护者：把 AI 审查前移到自己的 CI，在别人找到之前先找到；同时在 SECURITY.md 里写明报告必须附可运行的复现。

// 实战示例

# .github/workflows/security.yml：Anthropic 官方 action，只扫 PR diff
name: Security Review
permissions:
  pull-requests: write
  contents: read
on:
  pull_request:
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          fetch-depth: 2
      - uses: anthropics/claude-code-security-review@main
        with:
          comment-pr: true
          claude-api-key: ${{ secrets.CLAUDE_API_KEY }}
失败模式：README 自己写明这个 action 没有针对提示注入加固，只应审查可信 PR，并建议打开"外部贡献者需审批"——否则审查者本身就是 Day 24 讲的注入入口。它只看 diff，存量代码里的旧洞扫不到，需要定期对全仓再跑一次。误报过滤也会漏掉真问题，宁可多一轮人工确认。
进阶资源：anthropics/claude-code-security-review · LWN · Stenberg: The end of the curl bug-bounty program

// 术语表

Daybreak Blue / Red
OpenAI 网安准入的两档：Blue 给防御者放宽防护的通用模型（如 GPT-5.6 Sol），Red 给经审核团队专用网安模型（如 GPT-5.6-Cyber），需身份核验、监控、法律承诺与访问控制。
Fairwind
Google 发放 Gemini 3.8 Flash Cyber 的准入计划，优先政府、关键基础设施运营方与广泛使用软件的维护者。
Completion Rate（完成率）
模型对高风险网安请求的响应比例，衡量意愿而非正确性。
heap sandbox（堆沙箱）
V8 把堆对象限制在隔离区域内，即使出现内存破坏也难以触及区域外的内存；逃逸需要额外漏洞。
patch lag（补丁延迟）
修复版本公开到你实际部署之间的时间，是利用窗口里你能控制的那一段。
dependency cooldown（依赖冷却）
新版本发布后等待一段时间再采用，用来规避投毒包；Renovate 叫 minimumReleaseAge，Dependabot 叫 cooldown。
coordinated disclosure（协调披露）
先私下报告厂商、等修复发布后再公开细节的披露流程。

// 深入思考

能力分档 + 身份准入，会不会让攻防差距反而向攻击方倾斜？
准入门槛挡住的是守规矩的人。有组织的攻击方可以用开源权重模型、被盗账号或自建微调绕开，防守方却要排队审核。厂商的赌注是：放宽给已核验的防御者，能让修复速度跑赢开源模型能力的追赶速度。这个赌注成立的前提是防御者真的去用，并且修复能真正发布到下游。对个人开发者来说，更实际的结论是：不要指望拿到 Red，要假设攻击方已经拿到了同等能力。
专用模型报告变短，是能力退化还是对齐目标偏了？
更可能是训练分布的副作用：降拒答的数据大多是"直接给答案"的高风险请求，模型学到的是少铺垫、快交付，而好的漏洞报告恰恰需要铺垫（影响面、复现步骤、修复建议）。这提醒我们：微调目标里没写的质量维度，默认会被挤掉。如果你的流水线依赖报告质量，就把"报告完整度"写进自己的 eval，而不是相信模型名字里的 Cyber。
冷却期是一种"搭便车"，如果所有人都设 14 天会怎样？
冷却有效的前提是总有人先装、总有扫描器先看。如果人人都等，发现投毒的责任就全落在 registry 的自动扫描和少数早期采用者身上，第 14 天就成了事实上的首发日。这是典型的公共品问题，可以类比分布式系统里的退避：大家用同一个固定退避值会同步撞车，需要抖动。实践上，把关键依赖的冷却期设成不同长度，或者在自己的沙箱里提前跑新版本的测试，等于主动承担一点金丝雀的角色。
"没人维护的库被找到漏洞"这件事，个人能做什么？
三件事。盘点：依赖树里最后一次提交超过一年、只有一个维护者的包，列成清单。降暴露：能替换就替换，不能替换就收窄它接触的输入，比如只喂可信数据，或者放进隔离进程里跑。反哺：用 AI 找到问题时，附上复现和补丁一起提交，而不是只丢一份报告。在发现成本坍塌之后，"附带修复"才是对维护者真正有帮助的贡献。
