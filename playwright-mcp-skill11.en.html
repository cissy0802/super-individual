Browser-Automation MCP: Let the Model Read Structure, Not Guess Pixels

Playwright MCP taken apart · Accessibility tree vs screenshots · Where testing ends and scraping begins

2026-09-12 · BigCat

Same sentence — "click the login button." The screenshot route makes the model compute that it sits at (412, 318). The snapshot route only asks it to say ref=e47. One is a bet, the other is a pointer.

Related → Skill 10 Docs-Retrieval MCP (that category is read-only; this one can click, fill and submit)

// WHY THIS MATTERS

Docs-retrieval servers only move text into context. Browser-automation servers hand out a pair of hands that can click, type and submit. It is the widest permission jump of any MCP category — and the category most likely to look impressive and then never get used.

The subject is Playwright MCP (per its GitHub repo page, 2026-09: about 37.0k stars, Apache-2.0). But the part worth three minutes of your attention is not the install line — it is what separates it from every "screenshot plus coordinates" approach: it hands the model an accessibility tree, not pixels. Nine installable items below, and a last section on the question that matters most: when to install none of them.

// 01

What it kills for you: the round trip where you open a browser and click through it yourself

Claim: it does not replace your test framework. It replaces the loop where you switch to the browser, refresh, click three times, and paste the console error back. The real gain is that the model finally has an objective oracle — it can see for itself whether it broke something.

The first usage that actually runs

# (1) Install — this is the command from the official README
claude mcp add playwright npx @playwright/mcp@latest

# (2) A more restrained install: profile stays in memory, never hits disk
npx @playwright/mcp@latest --isolated --browser chrome

# (3) Say this first (start your dev server before you do):
Open http://localhost:5173, take a browser_snapshot first to see the
structure, click "Log in", fill demo / demo, then paste me the console
errors verbatim after submit.

Notice what that prompt does not say: "show me a screenshot." The official tool description for browser_snapshot is blunt — "Capture accessibility snapshot of the current page, this is better than screenshot" — and browser_take_screenshot closes the other road outright: "You can't perform actions based on the screenshot, use browser_snapshot for actions." In this design screenshots are for humans to look at, not for the model to navigate by.

Failure mode: installing it and then saying "go test my site." With no server running and no URL given, the model will navigate to an address it remembers and file a confident report about a page that does not exist. Start the server, give the URL — that is the entire reason with_server.py exists inside the official webapp-testing skill.

// 02

Mechanism: it works because it turns "that button" into a name you can cite

Claim: the difference between the two routes is not accuracy, it is how they fail. A wrong coordinate is silent and the model keeps going; a stale ref throws on the spot. One quietly manufactures a false conclusion, the other stops.
Two routes ──────────────────────────────────────────────────────────── Screenshot screenshot ──► model looks ──► guesses (412,318) ──► click_at needs a vision model · breaks on resize/scroll · fails silently Snapshot accessibility tree ──► role + name + ref=e47 ──► click(ref) plain text · citable later · stale ref throws immediately ──────────────────────────────────────────────────────────── The three official Key Features, verbatim: Fast and lightweight. Uses Playwright's accessibility tree, not pixel-based input. LLM-friendly. No vision models needed, operates purely on structured data. Deterministic tool application. Avoids ambiguity common with screenshot-based approaches. ────────────────────────────────────────────────────────────

Why it also happens to be cheaper

An accessibility tree is text, so the model can cite a node from it in every later step. A screenshot is an image: it demands vision capability, cannot be grepped, and cannot be referred to by name in the next sentence. Saving tokens is the side effect; being citable is the cause.

But snapshots are not universal

Canvas, WebGL, pure graphics, and "are these two elements aligned?" visual-regression questions have no corresponding nodes in the tree at all. That is exactly why --caps=vision (coordinate interaction) and the screenshot tools still exist — they are a complement, not a backup. chrome-devtools-mcp ships both take_snapshot and take_screenshot on the same division of labour.

Failure mode: asking the model to "look at the screenshot and tell me if the styling is right." It will say it looks tidy, and that sentence carries no constraint whatsoever. Style regressions need real visual diffing or written assertions — not a natural-language impression.

// 03

Real usage and limits: nine items in three layers

Claim: the usual mistake here is not picking the wrong tool. It is installing the testing layer and the scraping layer at once — after which four tools compete to answer "open a page" and you never know which path actually ran.

Layer 1 · Local drivers (get this layer right first)

  • @playwright/mcp. Kills: clicking through your own frontend after every change. Install: see section 01. The capability groups vision / pdf / devtools / config / network / storage / testing are all opt-in via --caps=; the default gives you the core group only. When not to install: when you have no page you can run locally, it is pure shelf-ware.
  • chrome-devtools-mcp (per its GitHub repo page, 2026-09: about 51.7k stars / 3.6k forks, Apache-2.0). Kills: recording performance traces by hand and staring at the Network waterfall. Install: npx -y chrome-devtools-mcp@latest, needs Node LTS and current stable Chrome. Its distinctive tools are performance_start_trace / performance_stop_trace / performance_analyze_insight / list_network_requests / get_network_request / lighthouse_audit / emulate (CPU and network throttling). When not to install: not if you only want to click things — its click / fill / navigate_page / take_snapshot overlap heavily with the item above, and running both resident means the model flips a coin every time. Two things to know: usage statistics are reported by default (--no-usage-statistics turns that off), and the performance tools may send trace-related URLs to Google's CrUX API.
  • --extension mode (Playwright extension, Chrome/Edge). Kills: re-doing a login flow just so the agent can see the page behind it. Install: add the extension, then npx @playwright/mcp@latest --extension to take over the browser instance you are already using. When not to use: when that same browser has your bank and your company admin panel open — it attaches to the whole instance, not one tab.

Layer 2 · Same capability, no server attached

  • Playwright Agents (official docs source file). Kills: making the model re-discover the same flow from scratch every session. Install: npx playwright init-agents --loop=claude (also vscode / codex / opencode), which sets up three roles — planner explores the app and produces a Markdown test plan, generator turns that plan into Playwright test files, healer runs the suite and repairs failing tests — landing in specs/ and tests/. When not to use: a one-off investigation you never intend to keep as a regression test. Then it is overhead.
  • anthropics/skills · webapp-testing (per its GitHub repo page, 2026-09: about 175.9k stars). Kills: the MCP connection itself — it has the model write Playwright Python directly. Install: /plugin install example-skills@anthropic-agent-skills. The core is scripts/with_server.py (--server "npm run dev" --port 5173 starts the server, then runs your script) plus a decision tree: for static HTML read the file and pick selectors, for dynamic apps call page.wait_for_load_state('networkidle') before inspecting. When not to use: if you need one browser context to survive across many turns, the server form is less work.
  • browser-use (per its GitHub repo page, 2026-09: about 114.3k stars, MIT). Kills: multi-step autonomous browsing ("go to this site, find X, fill the form"). Install: uv add browser-use as a library, or browser-use skill install to attach it to an existing agent as a skill — another case of the same capability shipped as a skill rather than a server. When not to install: anywhere you need control. An autonomous agent's strength is completion rate; its weakness is that you cannot predict what it clicked.

Layer 3 · Remote browsers and scraping (the boundary lives here)

  • Stagehand (per its GitHub repo page, 2026-09: about 24.2k stars, MIT). Kills: hand-writing a pile of brittle selectors for a one-off extraction. Install: npm i @browserbasehq/stagehand. The trio is act() for natural-language actions, observe() to find actionable elements, extract() for structured data against a Zod schema — and it mixes with ordinary Playwright locators. When not to install: when your selectors are already stable, a plain locator is faster, cheaper and more reproducible.
  • Browserbase MCP (hosted endpoint https://mcp.browserbase.com/mcp, six tools: start / end / navigate / act / observe / extract). Kills: needing a machine to run the browser on when you have none. Install: the hosted endpoint wants BROWSERBASE_API_KEY and BROWSERBASE_PROJECT_ID. When not to install: know this first — its open-source repo was archived on 2026-07-20 and its README says it should not be read as representative of the company's current production service. Use the hosted endpoint and check the vendor's live docs; do not configure from the archived repo.
  • firecrawl-mcp (per its GitHub repo page, 2026-09: about 7.4k stars, MIT). Kills: turning a batch of other people's pages into clean markdown. Install: npx -y firecrawl-mcp with FIRECRAWL_API_KEY; tools are firecrawl_scrape / firecrawl_search / firecrawl_crawl / firecrawl_map / firecrawl_interact. When not to install: if what you want is "click through my own app," that is testing, not scraping — use layer 1.
  • Counter-example: @modelcontextprotocol/server-puppeteer. Kills: nothing. It was an early MCP reference implementation and has been read-only in servers-archived since 2025-05-29. It is named here because a large number of tutorials still teach npx -y @modelcontextprotocol/server-puppeteer — the standard price of copying a blog without checking the repo's status.

Where testing ends and scraping begins

Your app, your source, assertions needed → layer 1 or 2, and the output should be a re-runnable .spec.ts. Someone else's site, data only, no assertions → layer 3, and the output is data. The test is simple: after this run, is there anything worth running again tomorrow? If yes, it was testing. If no, it was scraping.

Failure mode: keeping all three layers resident. browser_navigate from playwright-mcp, navigate_page from chrome-devtools-mcp, navigate from Browserbase and firecrawl_scrape all sit in the candidate list, and the model picks one each time. Keep exactly one per layer — the same discipline as last issue.

// 04

Costs and alternatives: it is not a security boundary — their words, not mine

Claim: the worst outcome from a docs server is a wrong parameter name. The worst outcome here is a click you did not authorize, inside a session you are logged into. The cost of this category is measured in permissions, not tokens.

Three red lines to know about

  • Verbatim from the README: "Playwright MCP is not a security boundary." It also ships a tool explicitly flagged as RCE-equivalent, browser_run_code_unsafe, which runs arbitrary JavaScript in the server process. Off by default — leave it off.
  • chrome-devtools-mcp is just as direct: it exposes the browser instance's content to MCP clients, which can inspect, debug and modify any data in the browser or DevTools, and it advises against putting sensitive information there.
  • The page body is an injection surface. Every word the model reads comes from that page, including instructions hidden in the DOM and addressed to an AI. The Claude Code MCP docs put it plainly: servers that fetch external content can expose you to prompt-injection risk. That is the subject of Skill 12.

Four knobs you can turn today

  • --isolated: keep the profile in memory, never on disk; pass an explicit --storage-state when you do need a logged-in session.
  • --allowed-origins / --blocked-origins: semicolon-separated allow/deny lists that pin down which origins the browser may request.
  • Do not enable --allow-unrestricted-file-access: what it opens up is files outside your workspace roots.
  • --caps= only the group this task needs. All seven capability groups being opt-in is itself the recommendation.

Three ways to install nothing at all

  • npx playwright codegen: you click through once, it records the code. For one-off verification this beats wiring up a server.
  • Put the tests in CI: whatever genuinely needs re-running belongs to CI, not to every conversation. That is precisely why the Playwright generator emits .spec.ts.
  • Paste the HTML: for a static page, pasting the source costs far less than a browser instance — and it is the first question in the official webapp-testing decision tree.
The honest cost: this is the category most likely to be installed, demoed once, and never used again. There is one criterion — in the past week, did it catch a frontend problem you had not seen yourself? If you cannot answer, remove it. The tool slots it occupies are far more expensive than a docs server's.

// ONE-PAGE BUYING CARD

Install these three first: (1) claude mcp add playwright npx @playwright/mcp@latest — no --caps at first, the core group is enough; (2) add npx -y chrome-devtools-mcp@latest only on the day you need performance and network data, and do not keep it resident alongside (1); (3) npx playwright init-agents --loop=claude to settle exploration into .spec.ts files under tests/.

Add as needed: npx @playwright/mcp@latest --extension (the day you need a logged-in session) · https://mcp.browserbase.com/mcp (when you cannot run a browser locally) · npx -y firecrawl-mcp (scraping other people's sites) · @browserbasehq/stagehand (one-off structured extraction) · browser-use skill install (when you want completion rate, not control).

Do not install: @modelcontextprotocol/server-puppeteer (archived 2025-05-29) · layer 1 and layer 3 resident at the same time · --allow-unrestricted-file-access · --caps=vision enabled "in case I need a screenshot."

One-line rule: if you can point with a ref, never click a coordinate; if anything from this run is worth running again tomorrow, write it as a test instead of having the model walk it again.

// GLOSSARY

accessibility tree
The structural tree browsers maintain for screen readers: every node carries a role (button, link, textbox) and a readable name. It was always a description of the page for non-visual users — which is exactly what a model needs.
snapshot ref
The short identifier (such as e47) a snapshot assigns to each interactive node. Later actions cite it instead of coordinates, and a stale ref throws immediately rather than clicking empty space.
capability (--caps)
Playwright MCP groups its tools by purpose and enables only the core group by default; vision, pdf, devtools, network, storage and the rest must be turned on explicitly. Every group you leave off is a tool tax you do not pay.
extension mode
Instead of launching a new browser, it attaches to the one you are already using — and therefore to the sessions you are already logged into. The convenience and the risk are the same fact.
performance trace
A recorded slice of runtime data from DevTools covering main thread, rendering and network timing. It is the real differentiator of chrome-devtools-mcp against general automation servers.
act / observe / extract
The trio used by Stagehand and Browserbase: perform an action, find actionable elements, pull data against a schema. The common shape of the scraping side.
networkidle
The state a page reaches once network requests have gone quiet. Reading the DOM of a dynamic app before this is the most common source of false negatives in this whole category.
