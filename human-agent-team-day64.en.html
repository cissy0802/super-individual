DAY 64 · TEAMWORK

The Agent on Your Team

An operating manual for human-agent co-development: how to hand off, how to review, where context lives, what to measure

2026-11-14 · BigCat

An agent can be the author. It cannot be the owner. Every agent PR needs a named person behind it.

Prerequisite → Day 34 Human-in-the-Loop Engineering · Day 33 AI Governance for Large Legacy Codebases

// WHY THIS MATTERS

People work with agents in three modes: synchronous pairing (one person steering one agent in an IDE), asynchronous delegation (assign an issue to a cloud agent, get a PR back), and the ambient teammate (tag it in a team channel, where everyone can watch and redirect). Claude Tag is an example of the third: you type @Claude in Slack, each thread gets its own temporary cloud sandbox, and code work usually ends in a draft PR (public beta, per its docs as read in 2026-11). Once the mode changes, the question shifts from how to use the tool to how to divide the work. This issue is a manual you can follow. Each of the four parts comes with a template you can copy, and a 30-day rollout checklist closes it.

// POINT 01

The task brief: replace "take a look" with a handoff you can accept

The quality of what an agent returns is capped by the brief you gave it.

// Background

Decide first which work can be handed off. All four tests must pass: the scope can be stated (you can list the directories), the agent can verify it alone (tests, lint, build), a mistake is cheap (a revert fixes it), and it needs no knowledge that lives only in people's heads.

Hand off firstHold back for now
Expired feature flag cleanup
Adding tests, fixing lint
Minor dependency upgrades
Docs that disagree with code
Small bugs with a stable repro		Cross-team interface design
Core paths with no test coverage
Schema, permissions, billing
Changes only production data can verify

A brief has five fixed fields: task, scope, done criteria, do not, when stuck. The done criteria must be commands or facts the agent can check on its own. Otherwise it will declare itself done.

// In practice

# One delegation message in the channel, all five fields present
@Claude repo acme/shop
Task: remove the flag checkout_v2 (fully rolled out for 30 days); keep the enabled branch
Scope: only checkout/ and its tests; no public interface changes
Done when:
  1. grep -r checkout_v2 returns nothing
  2. make test-checkout is green; paste the output in this thread
  3. a draft PR is open, with Requested-by: @alice and the list of removed branches
Do not: refactor along the way; touch other flags
When stuck: ask in this thread, do not guess
Failure mode: everyone in the thread can redirect the work. The Claude Tag docs state that anyone in the channel can steer a running session by replying in its thread, not only the person who started it. That lets anyone correct course, and it also lets a passing comment quietly widen the scope. Agree on one rule: only the requester changes scope and done criteria; everyone else adds facts. A second trap: progress shows as a checklist edited in place, and Slack sends no notification for edits, so a quiet thread does not mean nothing is happening.

// POINT 02

Review and accountability: a named person behind every agent PR

Whoever asks owns it, and whoever approves shares it. The author field says bot; the pager still goes to a person.

// Background

Rule one: the requester is the DRI (directly responsible individual). If something breaks after merge, the requester gets the call, so the PR description must carry Requested-by.

Rule two: close the path where one person does everything. The Claude Tag docs are direct about it: Claude is the author of the PR, so GitHub's rule against approving your own pull request applies to Claude and not to the person who asked. On a branch that requires one approving review, the requester can approve and merge alone. The docs offer two fixes: require two approvals, or add a required status check that only claude[bot] PRs must pass. With either, also dismiss stale approvals when new commits are pushed.

Rule three: tier by risk instead of holding every PR to the same bar.

TierExamplesWho approves
LowTests, docs, flag cleanupAnyone other than the requester
MediumBusiness logic changesThe CODEOWNER for that path
HighSchema, permissions, billingReview the plan first, then the diff

// In practice

# .github/workflows/agent-pr-second-review.yml (a sketch; try it in a test repo first)
# Bot-authored PRs must name a requester and carry an approval from someone else
name: agent-pr-second-review
on:
  pull_request: {types: [opened, edited, synchronize]}
  pull_request_review: {types: [submitted, dismissed]}
jobs:
  check:
    if: github.event.pull_request.user.type == 'Bot'
    runs-on: ubuntu-latest
    permissions: {pull-requests: read}
    steps:
      - env:
          GH_TOKEN: ${{ github.token }}
          PR: ${{ github.event.pull_request.number }}
          REPO: ${{ github.repository }}
        run: |
          REQ=$(gh pr view "$PR" -R "$REPO" --json body -q .body \
                | grep -oiE 'Requested-by: *@[A-Za-z0-9-]+' | sed 's/.*@//')
          [ -n "$REQ" ] || { echo "missing Requested-by: @user"; exit 1; }
          N=$(gh pr view "$PR" -R "$REPO" --json latestReviews -q \
              "[.latestReviews[]|select(.state==\"APPROVED\" and .author.login!=\"$REQ\")]|length")
          [ "$N" -ge 1 ] || { echo "need an approval from someone other than @$REQ"; exit 1; }
Failure mode: rubber-stamping. Once agent PRs pile up, review decays into clicking approve. Three countermeasures: no more than 3 agent PRs in flight per person; split any PR over 400 lines; deep-review two merged agent PRs every week. An AI first-pass review filters out mechanical issues, but it does not count as the approval from someone other than the requester.

// POINT 03

Shared context: write corrections into the repo, not into chat

A spoken correction covers this one run. A line in the instruction file covers every run after it.

// Background

An agent starts from zero every time and knows none of the team's tacit knowledge. The carrier is an instruction file at the repo root: AGENTS.md (a convention several tools read) or CLAUDE.md. Manage it like code: when an agent makes the same kind of mistake once, open a PR against this file and review it like any other change. What belongs in the file and how each tool loads it is covered in Skill 8; this section is only about how a team keeps it correct.

Four sections are enough, in order of value:

  1. Verification: which commands must run after a change, and how long each takes. This is the most valuable section. The more an agent can verify alone, the less a person has to act as the test harness.
  2. Off limits: directories and files that must not be touched.
  3. Conventions: how large a PR may be, whether behavior changes need a flag.
  4. Lessons learned: each with a date and a PR link, so it can be cleaned up later.

Large systems with slow verification need one more step: spell out the tiers (static checks in seconds, unit tests in minutes, replays in hours) and add the rule "if you cannot verify locally, stop and say what is missing." Without that sentence, an agent will hand back an unverified PR marked done.

// In practice

# AGENTS.md skeleton: only what an agent needs and cannot read from the code
## Verification (run after every change; paste results in the PR)
- make lint                 # seconds
- make test-<module>        # minutes; only the modules you touched
- Changes you cannot verify locally: stop and say what is missing

## Off limits (ask before changing)
- schema/**, billing/**, published *.proto fields

## Conventions
- One PR does one thing; split anything over 400 lines
- Behavior changes go behind a flag, default off
- PR description must include Requested-by: @requester

## Lessons learned
- <date> <one sentence>, see <PR link>
Failure mode: the instruction file grows into a wiki nobody reads. Rules contradict each other, one-off preferences get written down, and the agent follows the file less well. Prune it every quarter the way you prune expired flags, and split a long file into per-directory files. Also note that a running Claude Tag thread does not pick up a repository granted afterwards; the docs say to start a fresh thread after granting.

// POINT 04

Cadence and metrics: measure the queue before chasing speed

Once writing code gets fast, the time goes to waiting: for review, for verification, for release.

// Background

Three fixed rhythms:

  • Daily: requesters handle the agent PRs they started the same day. Nothing sits overnight.
  • A 20-minute weekly review: take each agent PR that was sent back or reverted, assign it one of four causes, and fix one thing per cause.
  • Always: one writer per module at a time, human or agent, claimed in the thread.
CauseWhat to fix
Unclear briefThe brief template
Missing team knowledgeAdd a line to AGENTS.md
Missing verificationAdd a test or a check
Should not have been handed offThe "hold back" list

Watch four numbers only: time from open to merge for agent PRs, first-pass rate (the share merged without human edits), revert rate after merge (compared with human-written PRs), and PRs in flight per person. Do not measure lines of code or total agent PRs. Those two only go up.

// In practice

# Agent PRs from the last 30 days: median hours from open to merge, and the share merged with a single commit (a rough proxy for first-pass rate)
gh pr list --state merged --limit 200 \
  --search "author:app/claude merged:>=2026-10-15" \
  --json createdAt,mergedAt,commits \
| jq '[.[] | {h: (((.mergedAt|fromdate) - (.createdAt|fromdate)) / 3600),
              c: (.commits|length)}]
      | {n: length,
         median_hours: (map(.h) | sort | .[length/2|floor]),
         one_commit_ratio: ((map(select(.c == 1)) | length) / length)}'
Failure mode: declaring success because output rose, without noticing that the review queue and the revert rate rose too. Large systems that release on a cycle of weeks need particular care: an agent delivers a PR in minutes, then it waits weeks in the same line as every other change. Adding agents at that point only lengthens the line. The investment that pays is a faster verification signal: tiered tests, flag-level rollouts, and an automatic verdict of safe, unsafe, or insufficient evidence.

// Crossovers

  • Psychology · diffusion of responsibility and social loafing: Darley and Latané found in 1968 that the more bystanders are present, the less likely any one of them is to help. In 1979 Latané and colleagues measured individual effort dropping as group size grew when people shouted and clapped together. A channel where anyone can steer the agent is that situation, which is why one requester gets named. The difference: the agent does not slack off. The reviewer who assumes someone else already looked does.
  • Complexity science · stigmergy: studying termite nest building in 1959, Grassé proposed that individuals coordinate without talking to each other, by leaving traces in a shared environment. Instruction files and threads are such traces. Unlike termite traces, stale rules do not evaporate; someone has to delete them.
  • Leadership · crew resource management (CRM): after the 1977 Tenerife disaster, aviation turned "will the first officer challenge the captain" into a trained skill. Letting anyone stop the agent in a thread is the same design. The difference is that here the party being challenged does not lose face.
  • Buddhism · sangha procedure (karman): the monastic community makes important decisions by announcing and asking for objections in front of the assembly; the fourfold procedure is one motion followed by three calls. A task opened and closed in a public channel puts the process in front of everyone in the same way. The difference: the procedure needs no objection from anyone, while a thread only needs nobody to hit stop.

// Ten takeaways

  1. People work with agents in three modes: synchronous pairing, asynchronous delegation, and the ambient teammate tagged in a team channel.
  2. A task is ready to hand to an agent only if scope is clear, it can self-verify, mistakes are cheap, and no tacit knowledge is needed.
  3. A task brief has five fixed fields: task, scope, done criteria, do not, when stuck. The agent must be able to check the done criteria itself.
  4. Anyone in a Claude Tag thread can redirect the work, so the team should agree that only the requester changes scope and done criteria.
  5. The requester is the directly responsible individual; an agent PR must say Requested-by, and that person gets the call if it breaks.
  6. On a branch that requires one approval, the requester can approve and merge Claude's PR alone; branch protection has to close that.
  7. Review in three risk tiers: any second person for low, the CODEOWNER for medium, plan review before diff review for high.
  8. When an agent repeats a kind of mistake, open a PR against AGENTS.md; its verification section is the most valuable part.
  9. A weekly review assigns each rejected agent PR to one of four causes (brief, team knowledge, verification, wrong handoff) and fixes one thing per cause.
  10. In a slow-release system, adding agents only lengthens the queue; the first investment should be a faster verification signal.

// 30-day rollout checklist

  1. Week 1 · guardrails: pick one channel and one repository; turn on branch protection and the Requested-by check; write a first AGENTS.md with only "Verification" and "Off limits"; record a baseline for the four numbers.
  2. Week 2 · small scope: hand off only tasks from the "hand off first" list, each with the five-field brief; requesters handle PRs the same day; at most 3 in flight per person.
  3. Week 3 · first review: assign a cause to every rejected or reverted PR and fix one thing for each; start the three-tier risk review.
  4. Week 4 · decide: compare with the baseline. If first-pass rate is high and revert rate is no worse than human PRs, widen the task types. If most of the time goes to waiting on verification, fix verification first and add no agents.

The one named person accountable for an outcome.
draft PR
A pull request marked as not yet ready to merge.
branch protection
Merge preconditions GitHub enforces on a branch, such as approval count and required checks.
CODEOWNERS
A repository file declaring who reviews which paths.
AGENTS.md
A file in the repository written for coding agents, read by several tools.
first-pass rate
The share of agent PRs merged without a human editing them.
stigmergy
Indirect coordination through changes individuals make to a shared environment.

// Think deeper

A requester can approve the agent PR they asked for. Loophole or reasonable design?
It depends on what you take the requester to be. As the author, it is self-approval and amounts to no review. As the first reviewer, the requester did read the diff, and that is a real review. The catch is confirmation bias: the requester framed the task and leans toward believing the result is right. So one person is acceptable for low-risk changes, and everything else needs a second pair of eyes.
If people write less and less code, can they still review it?
This is the team-level version of the skill decay problem in Day 59. Review ability comes from experience writing, and reviewing without writing erodes it over time. A workable practice is to keep some core modules hand-written and make the weekly deep review a fixed habit, not something done when there is spare time.
In a system where verification takes weeks, what is left of this manual?
The brief, the accountability rules, and the instruction file all still hold; they determine PR quality. What stops working is speed: the hours an agent saves are negligible next to a verification cycle of weeks. The right order for such a system is to make the verification signal fast and callable by an agent first, and only then widen agent use.
Should an agent have performance metrics of its own?
Setting them for the agent is pointless; it will not change its behavior in response. What does help is reading the same numbers as a health check on the team's process: a low first-pass rate points at the brief or the instruction file, and a high revert rate points at a verification gap. What is being evaluated is the system people built.
