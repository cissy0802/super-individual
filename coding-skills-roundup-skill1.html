// WHY THIS MATTERS

2025 年 10 月 Claude Code 上线 plugin 系统之后，skill（一个装着 SKILL.md 的文件夹，按需被 agent 读进上下文）从一个小功能长成了一整个市场：官方 marketplace、几家第三方 marketplace、无数「2026 年最好用的 N 个 skill」榜单。问题是这些榜互相打架——同一个「最流行」的位置，有的榜给的是一个 27 万 star 的框架，有的榜给的是一个装机量 764 的小工具。本期先把编码类 skills 的地形画清楚：它们其实分三种形态，混在一张榜里比是没意义的；再把官方那份《skill authoring best practices》反过来用——它是写给作者的，但每一条都能当买家的验货标准。这一期是本系列的开篇，后面几期会把榜上排第一的那个逐一拆开。

// 01

先分形态：方法论型、单点工具型、官方参考型

论断：编码类 skill 有三种完全不同的东西，装机成本、收益曲线、失败模式都不一样。把它们放进同一张榜排名，等于把操作系统和螺丝刀一起比销量。

背景与原理

① 方法论型（methodology-as-code）：不解决某一件具体的事，而是接管你的整个开发流程。代表是 Superpowers（作者 Jesse Vincent / @obra，MIT 许可）——它由十几个可组合的 Markdown skill 拼成一条强制流水线：头脑风暴 → 开 git worktree → 写计划 → subagent 分工实现 → 测试驱动开发（TDD）→ 代码审查 → 收尾合并。据其 GitHub 仓库页，2026-08 约 27.9 万 star；它 2025-10-09 与 Claude Code 的 plugin 系统同日发布，2026-01-15 被收进 Anthropic 官方 marketplace，另外还支持 Codex、Gemini CLI、Cursor、GitHub Copilot CLI 等多个 harness（harness=跑 agent 的那层壳，见术语表）。

② 单点工具型：一个 skill 干一件事，装完立刻能用。第三方 marketplace 的装机量榜基本被这类占满——据 Agensi 的安装量榜（2026-08）：code-reviewer（764 次安装）、git-commit-writer（232）、humanize-writing（192），往下是 readme-generator、pr-description-writer、prompt-engineer、env-doctor、changelog-generator、truth-first、skill-creator 等。

③ 官方参考型：Anthropic 自己的 anthropics/skills 仓库（2026-08 约 17.2 万 star），性质是「示范怎么写 skill」而不是「你该装什么」。它当前的 skills 目录里有 19 个，编码/产出相关的包括 docx / pdf / pptx / xlsx 四件套、webapp-testing、mcp-builder、web-artifacts-builder、frontend-design、skill-creator，另外还有 spec/（Agent Skills 规范）和 template/。

形态 代表 收益曲线 装机成本 最大风险 ────────────────────────────────────────────────────────────────────────── ① 方法论型 Superpowers 慢热，任务越大 高：它改变你 流程重，小任务 越划算 的工作方式 上纯粹是负担 ② 单点工具型 code-reviewer 立刻见效， 极低：一个 只在它命中的 git-commit-… 天花板也低 文件夹 那一步有用 ③ 官方参考型 anthropics/ 主要价值是 低 当「该装的清单」 skills 教你怎么写 来用就错了 ────────────────────────────────────────────────────────────────────────── 正确用法是「叠」不是「选」：① 定骨架 · ② 补高频动作 · ③ 当你写自己的 skill 时的模板

实战示例

三类的正确用法是叠而不是选：方法论型定流程骨架，单点工具型补高频动作，官方参考型当你自己写 skill 时的模板。真正要克制的是第二类——它单价低到你会一口气装十个，而代价在别处（见第 04 节）。

失败模式：① 看到「27 万 star」就装 Superpowers 去写一个 50 行的脚本——强制 TDD + 两段式审查会让你为一件十分钟的事付一小时；② 把 anthropics/skills 当应用商店，整仓克隆进本地，其中大半（algorithmic-art、slack-gif-creator、canvas-design）跟你的工作毫无关系。

// 02

「top rated」是个问句：三份榜差三个数量级

论断：装机量榜、star 榜、编辑推荐榜量的是三件不同的事。不问「哪个榜、什么时候、怎么数的」，排名就是噪声——而 SEO 聚合站连官方 skill 的名字都会写错。

背景与原理

把上一节的数字并排放：Superpowers 的 star 是六位数，第三方 marketplace 的榜首装机量是三位数。这不是「谁更受欢迎」，是分母完全不同——star 数着的是全 GitHub 的路人，装机量数的是某一个 marketplace 的注册用户，而「编辑推荐」数的是写稿人自己的偏好。三者不可比。

更实际的问题是二手来源会错。写这一期时，几篇 2026 年的聚合文章都把官方仓库的 skill 说成 artifacts-builder 和 slack-formatter——去仓库目录一看，实际叫 web-artifacts-builder 和 slack-gif-creator，后者根本不是格式化 Slack 消息的，是做 GIF 的。名字错了意味着你照着装会装不上，让 agent 照着找会找不到。

实战示例

给自己立一条硬规矩：任何要写进配置、喂给 agent、或者转述给同事的 skill 名，都以仓库目录或官方 marketplace 页面为准，聚合文章只用来发现候选、不用来抄名字。读榜时补三个问题——量的是什么（star/装机/下载）？哪个池子？数据是哪个月的？三个都答不上来的榜，当灵感来源就好。

失败模式：把某个 marketplace 的榜首当成「行业第一」写进团队规范；或者反过来，因为某个 skill「才 200 次安装」就否掉它——在一个几千人的 marketplace 里，200 次安装可能已经是该细分类目的天花板。
// 03

把官方的作者检查表，反过来当买家的验货单

论断：Anthropic 那份《Skill authoring best practices》是写给作者的，但它每一条都对应一个可以在三分钟内验证的购买判据——打开 SKILL.md 就能查。

背景与原理

先讲清楚机制，判据才成立：agent 启动时只把所有 skill 的 name 和 description 预加载进系统提示词，正文 SKILL.md 要等这个 skill 被判定相关时才读，其余附带文件再按需读——这套叫渐进式披露（progressive disclosure）。所以：description 决定它会不会被触发，SKILL.md 的长度决定它触发之后吃掉你多少上下文。官方给的硬约束是 name ≤ 64 字符（小写字母、数字、连字符）、description ≤ 1024 字符，正文建议控制在 500 行以内。

实战示例

克隆下来先查这六条，任何一条不过就别装：

  1. description 里有没有「什么时候用」：官方要求它同时写清做什么和何时用，且必须用第三人称（「Processes Excel files…」而不是「I can help you…」，因为它是被注入系统提示词的）。只写「Helps with code」这种，等于告诉模型「随便什么时候都可以用我」——它要么永不触发，要么到处乱触发。
  2. SKILL.md 有没有超 500 行：超了还不拆分文件，说明作者没做渐进式披露，你每次触发都在为没用上的内容付 token。
  3. 引用是不是只有一层：官方明确说 SKILL.md → reference.md 可以，但 reference.md → details.md 不行——嵌套引用时模型常常只 head -100 扫一眼，拿到残缺信息。
  4. 自由度是否匹配任务：官方的比喻是「悬崖窄桥 vs 空旷原野」。数据库迁移这种脆弱操作要低自由度（给死脚本、别改参数）；代码审查这种要高自由度（给方向，让模型自己判断）。一个把 code review 写成十二步死流程的 skill，是把原野当窄桥走。
  5. 有没有可执行脚本 + 校验闭环：确定性操作应该是预置脚本而不是让模型现编——更可靠、更省 token，而且脚本执行的输出才计费、内容本身不进上下文。质量攸关的地方还应该有「跑校验 → 报错 → 修 → 再跑」的循环。
  6. 有没有 eval：官方的方法论是先写评估再写文档——先记录没有 skill 时模型在哪失败，建三个场景当基线，再写刚好够用的指令。一个连「它解决了哪三个具体失败」都说不出的 skill，你没法判断它有没有用。

// 04

装多了的代价：context 税、触发打架、以及本该用别的东西

论断：单个 skill 的边际成本看起来只有几十个 token 的元数据，但 skill 的真正成本不在启动，在于选择——描述重叠的 skill 越多，模型挑错的概率越高。

背景与原理

渐进式披露确实让「装 100 个 skill」在启动时几乎免费。但官方文档也点明了另一面：description 之所以关键，正是因为模型要从上百个候选里挑一个。装十个描述互相重叠的编码 skill（一个 code-reviewer、一个 codex-grade-coding、一个 truth-first，都声称自己管代码质量），你制造的是一个选择问题，而不是能力叠加。

另一半代价是：你要的东西可能根本不该是 skill。三者的分工——

  • Skill = 往当前对话里注入「怎么做这件事」的知识。适合有稳定套路、需要模型按你的规矩来的任务。
  • Subagent = 起一个上下文隔离的分身去干活，只把结论带回来。适合会产生大量中间垃圾的探索（翻遍代码库找一个定义），主上下文不必被污染。
  • MCP server = 给 agent 接上外部能力与实时数据（查最新文档、开浏览器、读数据库）。skill 教不会模型它不知道的事实，MCP 可以。

还有第四个常被忽略的选项：hooks。「每次提交前都跑 lint」这种事该由钩子用代码保证，写进 skill 只是在祈祷模型记得。

实战示例

一个可执行的判断顺序：这件事每次都必须发生吗 → hook；需要外部数据或能力吗 → MCP；会产生大量不需要留在主上下文的中间过程吗 → subagent；只是「模型知道该怎么做就行」吗 → skill。

失败模式：把一份 API 文档做成 skill 塞进上下文——文档会过期，而且每次触发都吃 token；这是 MCP（文档检索类 server）的活。反过来，把团队的代码规范做成 MCP tool 也是错的，那本来就是纯知识，skill 才对。

// 一页选购卡

从三个装起，不要更多：① 一个方法论型（如果你的任务确实是多步骤的工程活）；② 一个高频单点型（多数人是 code review 或 commit/PR 描述）；③ skill-creator——因为你迟早要写自己的。

装之前三分钟验货：description 有没有写「何时用」且是第三人称 · SKILL.md 是否 < 500 行 · 引用是否只有一层 · 自由度是否匹配任务脆弱性 · 有没有校验脚本 · 说不说得出它解决的三个具体失败。

读榜三问：量的是什么？哪个池子？哪个月的数？——名字一律以仓库目录为准，别抄聚合文章。

装完两周复查：这两周它触发过几次？有没有一次是误触发？没触发过的直接删——留着只会让别的 skill 更难被选中。

// 术语表

Agent Skill
一个文件夹，里面必有 SKILL.md（YAML 头 + Markdown 正文），可选附带参考文档与可执行脚本。agent 按需把它读进上下文，用来学「怎么做某类任务」。
SKILL.md / frontmatter
skill 的主文件。开头的 YAML 头必填 name（≤64 字符，小写+数字+连字符）与 description（≤1024 字符）。
progressive disclosure（渐进式披露）
启动时只预加载所有 skill 的 name+description；正文触发后才读，附带文件用到才读；脚本只执行、内容不进上下文。这是「装很多 skill 也不炸上下文」的机制基础。
harness
跑 agent 的那层壳（Claude Code、Cursor、Codex CLI 等）：它决定上下文怎么组织、工具怎么暴露、skill 怎么被加载。同一个 skill 在不同 harness 上表现可以不同。
marketplace / plugin
skill 的分发渠道。plugin 是可以一次打包 skill + 命令 + hooks 的更大单位；marketplace 是列出这些包的目录站，官方与第三方各有。
subagent
由主 agent 派生、拥有独立上下文的子任务执行者，只回传结论。用来隔离会产生大量中间输出的探索。
MCP（Model Context Protocol）
让 agent 接外部工具与数据源的开放协议。补的是「模型不知道的事实与做不到的动作」，与 skill 补的「知识与套路」互补。
eval（评估）
一组「输入 + 期望行为」的测试场景。官方建议先建无 skill 的基线，再用它衡量 skill 到底有没有带来提升。
