SKILL 01 / CODING · ROUNDUP

Coding Skills Roundup

The ones people actually install — three shapes · who's on top · when not to install any of them

2026-08-29 · BigCat

"Top rated" isn't a fact, it's a question: which leaderboard? Three of them differ by three orders of magnitude.

Prerequisite → Day 17 Claude Code Advanced (what Skills / Subagents / Hooks / MCP each are)

// WHY THIS MATTERS

Since Claude Code shipped its plugin system in October 2025, the skill — a folder holding a SKILL.md that an agent pulls into context on demand — has grown from a small feature into a whole market: an official marketplace, several third-party ones, and endless "best N skills of 2026" lists. The trouble is that those lists contradict each other. The same "most popular" slot goes to a 279k-star framework on one list and to a tool with 764 installs on another. This issue first maps the terrain of coding skills: they come in three distinct shapes, and ranking them on a single list is meaningless. Then it takes Anthropic's Skill authoring best practices — written for authors — and runs it backwards, as a buyer's inspection checklist. This opens the series; later issues take the top entries apart one at a time.

// 01

Sort by shape first: methodology, single-purpose, official reference

Claim: coding skills are three different kinds of object, with different install costs, payoff curves, and failure modes. Ranking them on one list is like comparing an operating system and a screwdriver by unit sales.

Background & principle

① Methodology-as-code. Doesn't solve one task; it takes over your whole development process. The exemplar is Superpowers (Jesse Vincent / @obra, MIT). It is a dozen-plus composable Markdown skills wired into one enforced pipeline: brainstorm → git worktree → plan → subagent-driven implementation → test-driven development → code review → finish the branch. Per its GitHub repo page, roughly 279k stars as of 2026-08. It launched 2025-10-09, the same day as the Claude Code plugin system, was accepted into Anthropic's official marketplace on 2026-01-15, and also runs on Codex, Gemini CLI, Cursor, and GitHub Copilot CLI (a "harness" is the shell an agent runs inside — see glossary).

② Single-purpose tools. One skill, one job, useful the minute it lands. Third-party install charts are almost entirely this shape — per Agensi's install ranking (2026-08): code-reviewer (764 installs), git-commit-writer (232), humanize-writing (192), then readme-generator, pr-description-writer, prompt-engineer, env-doctor, changelog-generator, truth-first, skill-creator.

③ Official reference. Anthropic's own anthropics/skills repo (about 172k stars as of 2026-08) exists to demonstrate how to write a skill, not to tell you what to install. Its skills directory currently holds 19; the coding- and deliverable-adjacent ones are docx / pdf / pptx / xlsx, webapp-testing, mcp-builder, web-artifacts-builder, frontend-design, and skill-creator — plus spec/ (the Agent Skills spec) and template/.

shape exemplar payoff curve install cost biggest risk ─────────────────────────────────────────────────────────────────────────────────── ① methodology Superpowers slow start, high: it heavy process; wins big tasks changes how pure overhead you work on small tasks ② single-purpose code-reviewer instant value, near zero: only helps at git-commit-… low ceiling one folder the step it covers ③ official ref anthropics/ value is in low reading it as a skills teaching you shopping list ─────────────────────────────────────────────────────────────────────────────────── They stack, they are not alternatives: ① the skeleton · ② the frequent moves · ③ your template

In practice

The three stack; they are not alternatives. Methodology sets the skeleton, single-purpose fills in high-frequency moves, and the official repo is your template when you write your own. The one to ration is the second kind: it is cheap enough that you will install ten in a sitting, and the bill arrives elsewhere (section 04).

Failure modes: ① installing Superpowers because of the star count and then pointing it at a 50-line script — enforced TDD plus two-stage review turns a ten-minute job into an hour; ② treating anthropics/skills as an app store and cloning it wholesale, when most of it (algorithmic-art, slack-gif-creator, canvas-design) has nothing to do with your work.

// 02

"Top rated" is a question: three lists, three orders of magnitude

Claim: install charts, star counts, and editorial picks measure three different things. Without asking "which list, measured how, as of when", a ranking is noise — and aggregator sites get official skill names wrong.

Background & principle

Put the numbers side by side: Superpowers' star count is six figures; the top install count on a third-party marketplace is three figures. That is not a popularity gap, it is a denominator gap. Stars count every passer-by on GitHub; installs count the registered users of one marketplace; "editor's pick" counts the taste of one writer. The three are not comparable.

The practical hazard is that secondhand sources are wrong. While writing this issue, several 2026 aggregator articles named the official skills artifacts-builder and slack-formatter. The repo directory says otherwise: they are web-artifacts-builder and slack-gif-creator — and the latter makes GIFs, it does not format Slack messages. A wrong name means your install command fails and your agent's lookup misses.

In practice

Adopt one hard rule: any skill name you put in a config, feed to an agent, or repeat to a colleague comes from the repo directory or the official marketplace page. Aggregator posts are for discovering candidates, never for copying names. And ask three questions of any ranking — what is counted (stars / installs / downloads)? which pool? which month? A list that can't answer all three is inspiration, not evidence.

Failure modes: writing one marketplace's #1 into a team standard as "the industry leader"; or the reverse — dismissing a skill for having "only 200 installs" when 200 may be the ceiling of its niche in a pool of a few thousand users.
// 03

Run the author's checklist backwards, as a buyer's inspection

Claim: Anthropic's Skill authoring best practices is written for authors, but every item maps to a purchase test you can run in three minutes by opening SKILL.md.

Background & principle

The mechanism first, because the tests depend on it: at startup the agent preloads only the name and description of every skill into the system prompt. The body of SKILL.md is read only once that skill is judged relevant, and bundled files only when needed — this is progressive disclosure. So: the description decides whether it fires; the length of SKILL.md decides how much context it eats once it does. The official hard limits are name ≤ 64 characters (lowercase, digits, hyphens) and description ≤ 1,024 characters, with the body recommended under 500 lines.

In practice

Clone it, run these six checks, and skip it if any fails:

  1. Does the description say when to use it? The official guidance requires both what it does and when to use it, written in third person ("Processes Excel files…", not "I can help you…") because it is injected into the system prompt. A description like "Helps with code" tells the model it may fire at any time — so it either never fires or fires everywhere.
  2. Is SKILL.md under 500 lines? Over that with no file splitting means the author skipped progressive disclosure, and you pay tokens for material you never use.
  3. Are references one level deep? The docs are explicit: SKILL.md → reference.md is fine; reference.md → details.md is not — with nested references the model often previews with head -100 and acts on partial information.
  4. Does the degree of freedom match the task? The official analogy is a narrow bridge over cliffs versus an open field. Fragile operations like database migrations want low freedom (an exact script, don't add flags); code review wants high freedom (direction, then judgment). A skill that encodes code review as twelve mandatory steps is walking an open field like a bridge.
  5. Are there scripts plus a validation loop? Deterministic operations belong in bundled scripts rather than code the model regenerates each time — more reliable, and only the script's output costs tokens, not its contents. Quality-critical steps should have a run-validate → fix → re-run loop.
  6. Are there evals? The official method is evaluations before documentation: record where the model fails without the skill, build three scenarios as a baseline, then write just enough instruction to pass them. A skill whose author can't name the three concrete failures it fixes gives you no way to tell whether it works.

// 04

The cost of installing too many: context tax, trigger collisions, wrong primitive

Claim: the marginal cost of one more skill looks like a few dozen tokens of metadata, but the real cost is selection — the more skills with overlapping descriptions, the likelier the model picks the wrong one.

Background & principle

Progressive disclosure genuinely makes "100 installed skills" nearly free at startup. But the same docs name the other half: the description matters precisely because the model must choose one out of potentially 100+. Install ten coding skills with overlapping descriptions — a code-reviewer, a codex-grade-coding, a truth-first, all claiming code quality — and you have manufactured a selection problem, not stacked capability.

The other half of the bill: what you want may not be a skill at all. The division of labor —

  • Skill = inject "how to do this kind of task" into the current conversation. For work with a stable procedure that must follow your rules.
  • Subagent = spawn a context-isolated worker and get only the conclusion back. For exploration that generates a lot of intermediate noise (grepping a whole repo for one definition) without polluting the main context.
  • MCP server = connect the agent to external capability and live data (current docs, a browser, a database). A skill cannot teach the model facts it doesn't have; MCP can.

And a fourth option people forget: hooks. "Run lint before every commit" should be guaranteed by code, not written into a skill and left to the model's memory.

In practice

A usable decision order: must this happen every single time → hook; does it need outside data or capability → MCP; does it generate intermediate work the main context shouldn't keep → subagent; is it just "the model needs to know how" → skill.

Failure modes: packaging an API reference as a skill — it goes stale and costs tokens on every trigger; that is a job for a docs-retrieval MCP server. And the mirror error: exposing your team's code conventions as an MCP tool, when that is pure knowledge and belongs in a skill.

// One-page buying card

Start with three, no more: ① one methodology skill (if your work really is multi-step engineering); ② one high-frequency single-purpose skill (for most people, code review or commit/PR descriptions); ③ skill-creator — because you will end up writing your own.

Three-minute inspection before installing: does the description say when to use it, in third person · is SKILL.md under 500 lines · are references one level deep · does the degree of freedom match the task's fragility · are there validation scripts · can it name the three concrete failures it fixes.

Three questions for any ranking: what is counted, which pool, which month — and take names from the repo directory, never from an aggregator post.

Review two weeks after installing: how many times did it fire? was any of those a misfire? Delete anything that never fired — it only makes the remaining skills harder to select.

// Glossary

Agent Skill
A folder containing a required SKILL.md (YAML frontmatter + Markdown body) plus optional reference files and executable scripts. The agent loads it on demand to learn how to do a class of task.
SKILL.md / frontmatter
The main file. Its YAML header requires name (≤64 chars, lowercase, digits, hyphens) and description (≤1,024 chars).
progressive disclosure
Only every skill's name and description is preloaded at startup; the body is read on trigger, bundled files only when needed, and scripts are executed without their contents entering context. This is why installing many skills doesn't blow up the context window.
harness
The shell an agent runs inside (Claude Code, Cursor, Codex CLI…). It decides how context is assembled, how tools are exposed, and how skills load — so the same skill can behave differently across harnesses.
marketplace / plugin
Distribution for skills. A plugin is the larger unit that can bundle skills, commands, and hooks; a marketplace is the directory listing those bundles, official or third-party.
subagent
A worker spawned by the main agent with its own isolated context, returning only conclusions. Used to contain exploration that would otherwise flood the main context.
MCP (Model Context Protocol)
An open protocol connecting agents to external tools and data sources. It supplies facts and actions the model lacks — complementary to what a skill supplies, which is knowledge and procedure.
eval
A set of "input + expected behavior" scenarios. The official advice is to establish a no-skill baseline first, then use it to measure whether the skill actually helps.
